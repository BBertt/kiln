Editor loading flow: implementation plan

Issue #563 · plan written 9 November 2026 · status: LB-0, LB-1 and the LB-2 code are built and checked locally; staging and production remain · recording starts 30 November at the latest

Built 9 November The editor's loading flow now runs on one XState machine, and its diagram is generated and checked in make web-verify. The backend sends a phase key on the live stream and saves it on the build record (new nullable column, migration e8f2a6c4d1b9). The ten animations are wired. While the AI validates or repairs the site, a small animation in the testing badge keeps the preview visible.

Checked: web tests (1,161), backend unit tests (4,106), PostgreSQL tests for the build record (18), six Storybook journeys in a real browser, and the real editor on the local stack. On reload it recovered the writing step from the database, kept the preview visible while validating, and cleared when the build ended. Not yet checked: a live AI build, staging and production.

We will move the editor's loading and overlay logic into one statechart. A statechart is a state machine written as data: a list of modes and the events that move between them. Then we give each build step its own name on the wire, and use that name to show the right one of the ten new animations.

The work has four steps. Step LB-0 changes no visible behaviour. Steps LB-1 and LB-2 add the animations. Step LB-3 ships them to production before filming.

LB-0 · One declared flow first

Replace four separate pieces of loading logic with one XState machine. Add a generated diagram, machine tests and Storybook journeys. The screen looks the same as today.

LB-1 · A name for each step in parallel

The backend sends a fixed phase key next to each progress label. The editor stops guessing the step from the Indonesian label text.

LB-2 · Animations on staging

The machine picks one of the ten animations from the phase key. The file counter stays. Reduced motion stays.

Release to production. Jonathan watches one full build there before creators start recording.

What happens today

The editor decides what to show from many signals: the live chat stream, a saved "a build is running" record on the server, the deployment status that the editor asks for every 3 to 5 seconds, messages from the preview page, and five local timers. Four separate pieces of code combine these signals:

Piece of codeWhat it decides
usePreviewViewModelThe workspace status, and a 60-second timeout while the workspace starts.
usePreviewGenerationOverlayThe build overlay: shown, fading or hidden. It also holds a 4-second bridge after a build ends, until the server says files are syncing.
PreviewProviderThe wake-up overlay while the preview page starts, with a 30-second safety timer and an error panel.
PreviewContentA chain of if-statements that picks what is on screen from all of the above.

Nobody wrote down how these pieces work together. The order is only visible in the code. The editor also decides "the AI is testing the site" by comparing the label text with Memvalidasi… and Memperbaiki…. If someone changes the wording, that check breaks silently.

The ten animation components from #556 are in apps/web/src/domains/editor/preview/loading-animations/. No code uses them yet. Every wait still shows PreviewLoadingScene.

The target shape

The machine has three parts that run at the same time. A selector reads all three parts and returns the one scene to show. A selector is a small function next to the machine that turns its state into screen data.

This drawing is the plan. The real diagram is generated from the machine code and committed to docs/flows/editor-preview-loading.md. A test fails when the two differ.

The backend keeps its own state machine

XState runs only in the editor. The backend already has a state machine in Python, in apps/api/app/services/generation/turn/states.py. It decides which steps a build may take and how a build ends. We did not change it.

The new phase key is a separate, display-only signal. It says what the backend is doing now, so the editor can pick an animation. It cannot come straight from the backend's state: making images and syncing files have no state of their own, and a repair round plans and writes again but must still show "repairing".

Rules we keep

  • The server owns the truth about builds and deployments. The machine only receives what the editor already observes. It never starts or stops server work.
  • React Query keeps asking the server for status. The machine does not fetch data. The chat stream and the two Zustand stores stay as they are.
  • Server status, the stream, the saved build record and preview-page messages become named events. The three hooks that send them are thin. They hold no decisions.
  • Side effects have names in the machine, and the editor supplies them. Examples: "refresh the app status" when a build ends, and "send init to the preview page".
  • These stay outside the machine: reloading the preview when new files arrive, the keep-warm ping, and the history refresh after a recovered build. They are not loading or overlay decisions.

Storybook journeys

The journeys use the real machine and the real preview components. A fake editor backend replaces the server, in the same style as src/domains/onboarding/mocks/onboarding-backend.ts. A small stub page plays the preview page and sends "boot", "ready" or an error on demand. Each journey has a play function that checks each visible change.

  1. A build moves to syncing and then to a visible preview.
  2. Validating, repairing, then validating again.
  3. The build ends before the server reports syncing.
  4. The editor reopens during an active build.
  5. The wake-up overlay and the build overlay overlap, and the preview stays visible while the AI tests the site.

How it works: technical detail

This section explains the code that this work added or changed. It names files and symbols so that a reviewer can find them. The drawing in "The target shape" was the plan, with three parts. The built machine splits the same logic into five parallel regions, shown below.

Where the code lives

The tree shows every file that this work added, changed or deleted. Most of the frontend work is in one folder: apps/web/src/domains/editor/preview/. The backend's own state machine, turn/states.py, is shown for context. It did not change.

How a build phase reaches the screen

The backend sets a label and a ProgressPhase at each progress step. The phase travels two ways. The live chat stream carries it while the editor is open. The active_generations row saves it, so an editor that opens later reads it from the app GET. The editor gathers these inputs and the deployment status into one OBSERVE event. The machine decides what to show. A selector, selectPreviewLoading, turns the machine state into one screen. Green boxes are new.

The machine's five regions

The machine is in preview-loading.machine.ts. Each region tracks one concern, and all five run at the same time. A region moves when the observed inputs change (an "always" transition) or when one of its own timers ends. The machine owns every loading timer, so leaving a state cancels its timer. No component keeps a timer in a ref any more.

The exact, generated diagram is in docs/flows/editor-preview-loading.md. It shows every transition, guard and action name. A unit test rebuilds it from the machine and fails when the committed file is different.

Each build step and its phase

The label is display text for the chat. The phase is a fixed key for the editor. The backend's ChatTurnState is a third, separate value: it controls which steps the build may take. The table shows why the phase cannot come from the turn state.

Backend details

  • ProgressPhase is in db/db/models/enums.py. The API sends lowercase values, such as writing_code. PostgreSQL stores the enum member names, such as WRITING_CODE, which is how the existing enums in this repository work.
  • Migration e8f2a6c4d1b9 creates the progress_phase type and a nullable active_generations.phase column. Rows from before the change keep NULL, and the editor shows today's loading scene for them.
  • The label and the phase always change together, in ChatState.advance_progress for the stream and in ActiveGenerationRepository.touch_progress for the row. The heartbeat that keeps a long model call alive, refresh_alive, only moves last_progress_at. It cannot erase the phase.
  • When a build ends, the backend deletes the row in the same transaction that saves the reply and files. saving_files is written before that. updating_preview comes after, so it goes to the stream only and never creates a new row.

Frontend details

  • usePreviewLoadingViewModel is the only place that sends observations to the machine. It reads the live flag, the build-progress store, the saved marker and the deployment status, and sends one OBSERVE event when any of them change.
  • PreviewProvider starts the actor and listens to the iframe. It checks each message's source and origin before it sends FRAME_BOOT, FRAME_READY or FRAME_ERROR. The editor remounts the provider when the app changes, so a new app never sees the old app's timers.
  • The machine does not touch the browser or the query cache. It emits two named events, sendLifecycleInit and invalidateDeployment, and the provider performs them from an effect. Tests replace them with spies.
  • PreviewPhaseAnimation maps each phase to one of the ten animation components. saving_files and updating_preview use the Syncing animation. The animation is decorative (aria-hidden). The surrounding loading scene keeps the screen-reader label, the fade and the file counter.
  • React Query still polls the app GET, and the snapshot-version reload, the keep-warm ping and the recovered-history refresh stay outside the machine. They are not loading decisions.

Decisions

Issue #563 is ai::human-led, so Bertrand took these four decisions on 9 November 2026. Each one followed the recommendation.

1. How the saved build record keeps the phase

After a reload, the editor knows the build step only from the saved build record. Option A adds a phase column to active_generations. That needs a database migration, which needs a human approval under AGENTS.md. Option B makes the backend work out the phase from the saved label when it builds the response. Option B needs no migration, but the phase then still depends on the wording.

Decided: Option A Add a nullable phase column with a migration. The issue says that phase identity must not depend on display text.

2. Two labels with no animation

The backend also sends Menyimpan file… (saving files) and Memperbarui preview… (updating the preview). Both happen after the code is written and before the preview updates.

Decided: Own phase keys, Syncing animation They get saving_files and updating_preview, and both show the Syncing animation.

3. Whether the Storybook journeys run in CI

The Storybook test project in apps/web/vitest.config.ts is turned off today. With it off, the play functions run only when someone opens Storybook. Turning it on needs a Chromium browser in CI and makes the check slower.

Decided: Separate command first A command runs the journeys on demand, outside make web-verify. The machine tests are the gate. We add the journeys to CI later.

4. Odd behaviour found while mapping

The map found behaviour that is probably not intended:

  • The wake-up overlay does not check for testing. It can cover the preview while the AI tests the site.
  • The first-build scene ignores testing, so the preview stays hidden during the tests of a first build.
  • verifying is in the workspace status type, but nothing sets it.

Decided: Keep in LB-0, decide in LB-2 LB-0 promises no visible change. The generated diagram will show each case. We fix them in LB-2 only if Jonathan agrees.

Risks and limits

  • The Arsenal package comes from one small flow in Sitrep. Arcane is its second user. Our flow has more inputs and waits on long server work, which the package has not covered yet. We report what we learn back to Arsenal.
  • Today the frontend tests write labels with three dots (...), but the backend sends one ellipsis character (…). The phase key removes this problem, but some tests change in LB-1.
  • After a reload, the editor knows the phase but not the file counts. Writing code then shows no counter until the live stream returns.
  • Green tests and stories do not prove the real flow. The local stack and staging checks in LB-2 are the proof, and Jonathan's production check is the final one.

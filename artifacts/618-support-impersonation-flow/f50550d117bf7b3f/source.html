How support impersonation works in Arcane

A support person clicks one button in the admin console and sees Arcane exactly as a customer does. This page explains how the click turns into a customer session, and how it ends.

MR open, waiting for review IM-1 to IM-4 built Local check: 15 of 15 passed IM-5: not live yet Off everywhere until set up

The short version

In the examples below, Maya works in support and Grace is the customer. Three parts each do one job.

1 · admin console

Finds Grace's account

Maya types a reason. The console looks up Grace's Authentik id with a read-only token, then opens a link to Arcane.

2 · Arcane, /support/impersonate

Starts it on Arcane's host

Arcane shows Grace's name and the reason. Maya presses Mulai. Arcane asks Authentik, as Maya, to switch her session to Grace.

3 · banner on every page

Shows it and ends it

"Kamu melihat sebagai Grace" stays visible. Berhenti ends the impersonation and signs Maya out.

Authentik decides who may impersonate. Maya needs her own view_user and impersonate permissions. Neither the console nor Arcane holds a credential that can impersonate anyone.

Why it broke

Authentik remembers an impersonation inside the browser's Authentik session cookie. A cookie belongs to one host. Since ADR-063, Arcane's sign-in reads the Authentik session on Arcane's own host, not the one on auth.…. So an impersonation started in Authentik's admin page is invisible to Arcane.

Each column shows the browser's cookies for two hosts. The tags show where the impersonation started and which session Arcane's sign-in reads.

The admin console cannot fix this from its side. It is a different site, so the browser sends it no Authentik cookie for Arcane's host. A call from the console's server would impersonate inside the console's own session, not Maya's browser. The impersonation has to start on Arcane's host, in Maya's browser.

Starting: the full path 15 steps · 4 phases

Solid arrows are requests. Dashed arrows are answers. A small circle on Arcane's line means the browser call goes through Arcane's same-origin proxy (/ak/…) to Authentik, so Authentik sees Maya's own cookies.

    Two sessions, and why the order matters

    Arcane has two sessions in the browser. The Authentik session says who Maya is to Authentik. Arcane's own session (next-auth) is a copy of it, taken at sign-in. Starting and stopping must move both, in the right order.

    Read left to right. The red dashed columns are short moments where the two sessions disagree.

    Two easy mistakes the order avoids

    • At step 3, the normal sign-out would end the whole Authentik session, and the impersonation with it. So the page clears only next-auth's session.
    • At step 5, ending the impersonation alone would leave Grace's token in Arcane's session. So the normal sign-out follows, and ends both.

    Who gets in: the checks

    Anyone can open the link. These checks run in order. A customer who finds the link sees only Arcane's normal 404 page, so the page does not reveal that the feature exists.

      Stopping: the banner

      The banner is mounted in Arcane's root layout, so it can appear on every page. It only asks Authentik when a small marker cookie exists. Ordinary customers never carry the marker, so their pages make no extra call. The banner trusts Authentik's answer, never the marker.

        If Maya closes the tab without pressing Berhenti, the impersonation stays on in that browser. The banner comes back the next time she opens Arcane there.

        How the console finds Grace's Authentik id

        Authentik's impersonate call needs Grace's pk, Authentik's row id. Arcane's database stores only her OIDC sub, usually a hash that Authentik's user list cannot search. The console bridges the two with a read-only token, through an interface called IdentityProviderAdmin. A move off Authentik (#548) replaces one class behind it.

          The match must be exact. The search starts from a sub that Arcane stored, so it cannot reach an account that never signed in to Arcane, such as a SiteProtect-only account on the shared Authentik.

          Limits and open risks

          • The feature is off in every deployed environment. The console's Ansible role does not set ADMIN__IDENTITY_PROVIDER__* yet, and the shared Authentik needs the support role and the console's token. Both are Jonathan's call.
          • The console's token can read every user on the shared Authentik, SiteProtect's included. The code limits the lookup; the permission itself is not narrower.
          • The reason travels in Arcane's link, so it lands in browser history and access logs. Use ticket numbers, not customer details.
          • A support person whose role is missing also gets the 404, as does anyone when Authentik does not answer. The runbook explains this.
          • An impersonation started outside the page, with hand-made API calls, shows no banner, because the marker cookie is missing.
          • While impersonating, Maya can do everything Grace can. A read-only mode is out of scope.
          • Staging has not been tried yet. A support person must run it there before IM-5.

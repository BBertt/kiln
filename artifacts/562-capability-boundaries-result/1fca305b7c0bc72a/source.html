01

A capability boundary, not a page boundary

Business-oriented names are useful when they identify a lasting capability. “Campaign controls” remains an operator-facing page name—not the owner of platform-wide AI configuration.

API consumerAdmin consumerArrows = imports / uses

Credits → neutral store

SignupCreditPolicy owns defaults and validation. It uses the runtime override store; runtime settings does not import credit policy.

Audit stays in admin

Shared commands return before/after values. They do not import admin principals, activity types or the audit table.

Frontend follows capabilities

Settings imports runtime features—not CampaignControls.tsx. Activity formatting and commercial helpers also have separate homes.

02

Two writes. One transaction.

Operator identity and the reason belong to console orchestration. Validation and business mutation belong to the capability. Both database writes use the same session.

Unchanged refusal semantics. Stale saves answer 409; invalid values and duplicate coupon/promo creation answer 422. Reloading stale state preserves the operator’s draft and reason.
03

A new operation sees the new settings

A configuration change is not a campaign switch. Model, image and generation overrides are resolved by the API for each new operation; an in-flight operation retains its snapshot.

  • Empty model fields return to deploy settings; empty fallback lists mean no fallbacks.
  • Signup credit policy is resolved separately, inside the existing provisioning transaction.
  • Existing purchases, subscription terms and granted credit lots retain their snapshots.
  • Provider credentials stay with the API. The console receives presence checks, never keys.

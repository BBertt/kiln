Arcane · Issue 610 · RFC-032 spike · 10 November 2026

The cluster can run the browser runner as designed.

The Kubernetes service proxy, readiness routing, the access right and network policies all work. Six details in RFC-032 must change before phase 4.

A spike is a short test that proves or kills an idea before people agree on it. This one ran for about two hours on the shared cluster, in its own namespace, and then deleted everything it made. The page moves to Outline later.

Verdict: go. The direct request through the Kubernetes API works for a 180-second check, so the start-then-ask fallback is not needed.

One finding falls outside RFC-032 and needs a decision: no network policy exists in the cluster, and a pod without one reached the staging database's port. See the last section.

What the spike ran

The spike created the namespace browser-runner-spike on the cluster that serves dev, staging and production. It held a dummy runner with two replicas, two probe pods, a test service account, a role, and two network policies. It did not touch any existing object.

The dummy runner had no browser. It held one request at a time, answered "not ready" while busy, and logged when a caller closed the connection. A separate pod ran real Chromium against one awake dev preview.

All calls went from this workstation through https://k8s.arcane.jmn.my.id/api, the same address that the API uses. They used the test account's token, not the platform token. The two replicas landed on different worker nodes.

5. Network policies

The cluster runs Weave Net 2.8.1 with its policy controller. The spike tested reachability from a probe pod in three states: no policy, the RFC's policy, and the RFC's policy plus an allow rule for the Traefik namespace. The RFC's policy allows DNS and public addresses, and blocks private ranges, the metadata address and everything inside the cluster.

The preview host resolves to two public addresses. One of them, 103.185.38.113, is the cluster's own load balancer for Traefik. Inside the cluster, Kubernetes rewrites it to a Traefik pod address, which the RFC policy blocks. With both addresses pinned and the Traefik rule in place, all six preview requests returned 200.

The runner's ingress policy allowed only the source address that proxy traffic arrives from, 10.239.192.2, the control-plane node's Weave address. The service proxy kept working, and a pod outside every policy did not reach the runner. A rule on one address breaks if Weave gives the node a new one, so the infrastructure review must confirm it or find a steadier rule.

Traffic from a pod to the kubelet on its own node is not filtered. The kubelet on the other node was blocked.

6. Chromium in a locked-down pod

The pod ran the Playwright 1.59.0 image as a user that is not root, with no extra privileges, a read-only root file system, the default seccomp profile, and the RFC's 2 CPU and 2 GiB. The nodes use cgroup v1.

With its sandbox on, Chromium did not start: BrowserType.launch: Target page, context or browser has been closed. With the sandbox off, it opened four routes of a dev preview, two at a time:

That is about 5.3 s per pair of routes, close to the 4.7 s that RFC-032 §3.3 projects from production. The pod's memory rose from 210 MiB to at most 437 MiB during the run, which includes the installer's cache. Two pages fit well inside 2 GiB. One small app is not enough to lower the limit.

Changes for RFC-032 and the plan

  1. The client calls services/browser-runner:http/proxy, and the role lists browser-runner:http by name.

  2. The front proxy ends every request at 300 s. The 180 s deadline, clean-up and network must stay under it, and the RFC must name this ceiling.

  3. The API client keeps one pool of open connections, so a check does not pay about 1.1 s to connect.

  4. The egress policy also allows the Traefik namespace. The ingress rule for proxy traffic needs an infrastructure decision, because it uses one node address.

  5. Chromium runs without its sandbox, and the pod's limits stand in for it. After each check, the runner kills every other process in its container and empties its writable folders. Decided on 11 Nov and added to RFC-032 §3.8.

  6. RFC-032 §7 questions 1 to 3 are answered: the service proxy works, policies are enforced, and the cluster has room. The plan's infrastructure gate becomes the review of these findings.

A finding outside RFC-032

No network policy exists anywhere in the cluster. Without one, the probe pod reached the staging managed Postgres port, other preview pods directly, the Kubernetes API service, and the kubelets. The spike only opened TCP connections and sent no data.

[INFERENCE] Preview pods run generated code on the same network without any policy, so they can likely reach the same targets. The spike did not test from a preview pod.

This needs a separate issue and a human decision. It is infrastructure and security work, outside #610.

Cleanup: the namespace browser-runner-spike and everything in it were deleted, and the cluster again has no network policies. The test token expired with its service account. Local scripts were removed.

Limits: calls came from this workstation, not from the platform host. The dummy runner had no browser, and the Chromium test used one small dev app. Nothing ran in staging or production namespaces.

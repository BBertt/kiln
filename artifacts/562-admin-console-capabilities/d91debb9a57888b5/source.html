01The issue and the MR are not the same-sized change

The issue’s outcome

Operate without a deploy

  • Change plan prices, signup credits, coupons and promo claim links.
  • Switch the models used for the platform’s AI roles.
  • Require a reason and preserve who changed what.
  • Open a customer app’s real preview and published-site URLs.
The broader MR

A larger platform-console rebuild

  • Runtime image and repair budgets; a broader settings readout.
  • Console-wide activity, cross-app generation runs and the new read-only Jobs page.
  • Rebuilt Overview, Customers, Applications, Payments, Sales and Model usage.
  • Light, Dark and Indigo themes, plus shared UI improvements.
Scope review is still separate from implementation. The MR explicitly calls out the Jobs page, themes, other platform-page redesigns, repair-model removal and product-API changes as beyond #562 and needing sign-off. ADR amendments record owner approval for several settings, promo and audit extensions; that does not make the whole larger MR approved or released.

Not all of this is new product functionality. Credit grants/reclaims, quota overrides, sandbox payment simulation, code-version export and the session-only FX calculator already existed. This MR augments some of them with audit/reason requirements or a redesigned read surface. Customer/application detail pages were not wholesale redesigned.

03What changed behind the interface

The admin frontend talks to its own backend. That backend reads shared records, performs narrowly permitted writes, and asks the customer API only for provider checks and a settings report. The customer API and workers must also consume the saved values; otherwise the controls would merely edit unused rows.

Solid paths: console requests and database effects. Dashed path: narrowly scoped API checks/reporting, not a customer or general admin credential.

1 / Durable homes

The migration adds runtime_settings with JSON values and revisions, admin_control_changes for attribution, and an active flag on coupon billing-variant rules. Prices, coupons and promos stay in existing business tables.

2 / Real consumer wiring

A single model-role contract replaces scattered startup settings. API dependencies, streaming, classifiers, ideation, suggestions, module selection and image work consume resolved role values. Signup provisioning reads its credit policy in its existing transaction.

3 / Safe direct writes

Shared commands lock the target, validate and compare the reviewed state; runtime settings also compare revisions. The admin backend records authenticated actor, reason and effective before/after values in the same transaction for direct database changes.

4 / Narrow trust and grants

Keep read-only and named-write database identities separate. Reuse the admin group, not a new permission system. A dedicated paired service token permits model checks and reporting; no provider key is copied to the console.

5 / Richer read projections

New or expanded jobs, run-summary, category, payment-option, unplaced-callback, health and usage reads turn existing records into operator-facing facts. Some schedules are pinned restatements, not live scheduler configuration.

6 / Reporting is not a new setter

The API reports actual startup settings and code constants. QRIS expiry and generation credit cost were named/exported for this report without changing their values. The Unleash addition reads cached state; it does not write flags.

No deploy does not mean retroactive

New purchases use new catalogue economics; existing purchases and subscription billing terms keep their accepted snapshots. New signup grants use the new policy; existing lots are not rewritten. Promo edits affect later claims.

The UI also gained refusal and recovery behavior. Every control change needs a nonblank reason. A stale save answers 409; invalid values and duplicate creates answer 422. “Reload current value” preserves the draft and reason. Clearing model overrides restores their baseline; an explicitly empty fallback list means no fallbacks.

04Visible does not mean writable—or fully backed

These are different situations: an intentional read-only boundary, configuration not provisioned, an existing platform action not delegated to this console, missing data, a frontend-only calculation, or an actual wording/failure-boundary caveat. They should not all be described as “the backend is unfinished”.

05Implemented is not the same as accepted in production

Rollout prerequisites

Make the backing services available

  • Apply the additive migration before the new application versions.
  • Provision named write grants, including promo management and INSERT-only activity history; no DELETE grant.
  • Configure the paired model-availability token and the console’s API origin.
  • Set the customer web origin for complete promo claim URLs.
  • Migrate API and worker environment keys to MODELS__*; remove stale MODELS__REPAIR before booting the new image.

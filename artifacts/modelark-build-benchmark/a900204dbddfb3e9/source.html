Which model should build the site

Eight models, five futuristic briefs, three runs each, through the production plan-and-write pipeline. Every build was rendered, checked against its brief, and reviewed blind. Round 2 replaces round 1's result.

issue 638 MR !737

DeepSeek V4.1 Flash should take the build slot. It passed every check on 13 of 15 builds and scored 22.5 of 25 in the blind review, the best mean of the eight models. Seed 2.1 Turbo passed one more build on all checks (14 of 15; both are 14 of 15 on validation) but scored 17.4, so it is the more reliable model with the weaker sites.

The finding that matters more is about Gemini. In 21 of its 23 failures, Gemini put the database schema in the wrong place in the tool call. Our argument model drops unknown fields without an error, so no migration was written, no collection was created, and the turn still ended ok. Production builds every app with Gemini 3.7 on app-base, so this likely ships apps without a database today. That is an inference until someone checks production run history. The key finding has the details.

Fairness

62 failures were the model's own, 1 was harness-caused and 0 were the fixture's. The harness-caused one is a GLM 5.3 Flash run that hit the provider's per-minute token quota. Every collection name and route a check expects is named word for word in its brief.

Invalid tool calls

Counted from run logs, not the eval summary, which only records the final turn state. DeepSeek V4 Pro's 11 are mostly 300 s provider silences. GLM 5.3 Flash's 25 include 16 write streams that were not valid JSON.

Cause key: schema nested means the database schema sat inside plan and was dropped. No schema means nothing was declared. Missing collection means some expected collections were never declared. English names means the model declared collections under translated names. Broken write JSON means write arguments did not parse against the tool schema. Out of time means the turn's 900 s allowance ran out.

Code changes GLM and Seed need round 2 ran them with a local patch

Round 2 did not run the merged pipeline. GLM and Seed ran with a local patch, applied for the benchmark only and not in the branch. Without it, the GLM and Seed results in this report would not exist: round 1 showed both families unable to finish a build at all.

GLM 5.2 and GLM 5.3 Flash

Two changes, both needed before either model can hold the build slot.

  1. A tool-argument parser change. With our $ref-based tool schema, GLM sends nested objects as JSON-encoded strings instead of objects. We proved this against ModelArk directly and through LiteLLM, so it is the model's shape, not our transport.
  2. An explicit output limit. The pipeline sends max_tokens for these models, set to the documented maximum, so ModelArk's 4096 default cannot truncate a write.

Seed 2.0 Pro and Seed 2.1 Turbo

One change: the same explicit output limit. ModelArk defaults max_tokens to 4096 for every model except DeepSeek V4.1 Flash, and that default cut Seed's file writes off in round 1. The patch sets the model's own maximum.

Gemini and both DeepSeek models

No change. Their requests were untouched, so they ran the same pipeline as in production. Round 2 uses new briefs and the app-base template, so its numbers are not directly comparable with round 1's.

What the patch did not fix

  • GLM 5.2 still fails at the write gate. Three of its runs sent files as one JSON string; the write gate rejected it with Input should be a valid list. The patch decodes JSON-encoded containers, but these payloads arrived double-encoded or with trailing text, and by then the turn had spent 900 to 1470 s and had no retry left.
  • Seed's broken write JSON. Four Seed 2.0 Pro runs ended in IncompleteJSONError: parse error: trailing garbage; the patch does not touch invalid JSON.
  • Volume and time. GLM 5.2 waits 1171 s at the median and writes for up to 1104 s, so it runs out of the 900 s turn even when its arguments are valid.
  • Collection naming. Seed 2.0 Pro declared frames, stalls and houses where the briefs say rangka, warung and rumah. That is a reading error, not a parser one.

What could not be tested

  • The patched path in production. The two code changes above are local. Nothing here proves them in the merged pipeline.
  • Bill separation. The benchmark ran on a dedicated benchmark-only BytePlus API key. Whether ModelArk's usage data can tell that key's spend apart from the staging key's is not verified yet; we did not confirm it, so treat cost reporting as open.
  • Production run history. Nobody has checked whether the Gemini nested-schema defect is already shipping apps without a database. The key finding is an inference until that check runs.
  • Gemini with a fixed pipeline. Accepting the nested schema would probably recover 21 runs, but that variant was not built or measured.
  • Turns after the build. Every run is a first build. Edit turns, follow-ups and long conversations are not measured.
  • Journeys. The harness checks structure, collections and routes, not whether a checkout saves an order. Reviewers read the code for faked writes.
  • Admin screens. The harness does not sign in, so admin pages were judged from source.
  • Images. Every build got the same fixed photographs, so this measures image placement, not picture choice.
  • Throughput. Two to four builds ran at once on one account. That is not a rate-limit test; one GLM 5.3 Flash run still hit the per-minute quota.

Recommendation

Put DeepSeek V4.1 Flash in the build slot. It is the only model that is both reliable and good: 13 of 15 builds passed every check (87%), and its blind mean of 22.5 of 25 is 2.3 points clear of the next model. It reached 25 of 25 once and 24 five times. It wins 13 of the 15 site-and-run groups, 11 of them outright. It needs no code change: its requests are unchanged from round 1.

Yes, switch staging under BP-4. Run DeepSeek V4.1 Flash as staging's plan and write model, keep the existing fallback chain, and compare on staging's own traffic before production changes. Because V4.1 Flash needs no patch, the switch does not wait for the parser work.

Land the two pipeline changes before GLM or Seed are tried again. The explicit output limit and the JSON-string decode are what let GLM and Seed finish a turn at all. They are small and model-specific: one table keyed by model id, one decode at the argument boundary. They are not part of this benchmark's merge request.

Fix the nested schema and check production. Accept database_schema inside plan, or reject it with an error the model can act on. Either way, file a follow-up issue and read production's Gemini 3.7 run history to see how many shipped apps have no collection behind their data. This is the most urgent item on the page: it is a silent failure in the model we ship today.

Leave GLM and Seed out of the slot. Seed 2.1 Turbo is the second most reliable model but scores 17.4 on quality and needed 6 repair rounds. GLM 5.3 Flash passed nothing.

Alternatives, and why they lost

Seed 2.1 Turbo — 14 of 15, blind 17.4

The most reliable model on the page and the second fastest. It lost on the sites themselves: structure 3.07 of 5, six repair rounds, and one run at 999 s. Reliable output that reads like a template is not a reason to switch.

DeepSeek V4 Pro — 10 of 15, blind 20.2

Higher than Flash on persistence honesty (4.25 against 4.07) and structure (4.5 against 4.4); Flash is ahead on fidelity, design and copy. It lost on time: a median build of 1067 s, four times Flash's 252 s, and 3 turns ran out of time. Its writes are 57k output tokens a build, so it is slower and dearer for a slightly worse site. Its mean also covers only its 12 completed builds, so the 3 timeouts are not in it.

GLM 5.2 — 6 of 15, blind 18.5

Its best build scored 22 of 25 and three more scored 20, but a 1171 s median and three writes rejected as a JSON string make it unusable as the default. It needs both code changes plus a smaller plan.

Seed 2.0 Pro — 7 of 15, blind 13.5

The fastest model at 180 s a build. It names collections in English, breaks its own write JSON in four runs, and scores 2.45 on structure. Speed did not translate into a working site.

GLM 5.3 Flash — 0 of 15, blind 8.0

No site passed. Its plan alone takes 388 s at the median, and 8 runs died on write streams that were not valid JSON. Two builds reached the reviewer and scored 8 of 25.

Gemini 3.8 Flash and 3.7 Flash — 4 and 3 of 15, blind 13.1 and 13.0

The current build models. Both lost to the nested-schema defect, not to design: design scores of 3.43 and 3.33 are respectable, but persistence honesty is 1.43 and 1.47. Fixing the pipeline would recover most of their failures, and that fix should ship whether or not the model changes.

Method and limits

Eight models ran the production pipeline through the eval harness: the plan step and the write step used the model under test, while the safety classifier, the module picker, the design lookup and the image model stayed as production keeps them. Fallbacks were switched off, so a model that failed could not finish on another model's work. Repair rounds stayed on, as in production, and a turn had 900 s of wall clock.

Each build started from app-base, the template production uses since ADR-043, and ran in Docker with PocketBase live. Playwright then loaded every route, scrolled it, waited for images and screenshotted the full page. Five briefs times three repeats times eight models gives 120 turns on 13 and 14 November 2026, on one dedicated benchmark key, with two to four builds running at once.

Review used one blind reviewer per site and run: 15 reviewers, all Claude Opus 5.5, a model not under test. Round 1 used Claude Sonnet, which was not available for round 2, so the two rounds' scores are not directly comparable. Reviewers got sanitized copies with the model names removed and scored five criteria out of 5: fidelity to the brief, persistence honesty (does a save really save), structure, design and copy. Builds that rendered nothing were not reviewed, which is why 93 of 120 have a score.

Limits: no edit turns, no journey tests, no admin sign-in, one fixed image set, 2 to 4 concurrent builds on one account, one reviewer per group, and a local patch for GLM and Seed. Reproduce with uv run python scripts/benchmark/02_run.py, then 03_score.py and 04_review.py.

Key finding: Gemini drops the database schema 21 builds, no error

Gemini sends the schema one level too deep. CreatePlanArgs expects database_schema beside plan; Gemini puts it inside plan. The argument model ignores unknown fields, so the schema disappears without a warning, no *_ai_msg_*.js migration is written, and the collection the app queries never exists. The turn still ends ok.

{ "plan": {
    "editable_files": [...], "actions": [...],
    "database_schema": { "tables": [ { "table_name": "jendela_orbit" } ] } } }

The pattern is exact. All 7 Gemini builds that passed declared the schema at the top level and wrote a migration. All 21 collection failures had it nested and wrote none. DeepSeek V4.1 Flash passed all three orbit-nusa runs with the identical brief by declaring the schema at the top level.

The result is worse than a blank page. In three of the five briefs the app really does read and write the named collection, so every read and submit fails and the errors are swallowed into an empty list: the site looks empty but healthy. In two pasar-neon runs Gemini also mirrors the write into localStorage and returns success, so an order appears to be placed and nothing is stored.

Production runs Gemini 3.7 Flash on app-base for every app. The same tool schema and the same argument model are in that path, so production likely ships apps with no database today, and their data screens fail quietly. This is an inference from the run artifacts. We have not read production run history. Recommended follow-up: a separate issue that (1) accepts or explicitly rejects plan.database_schema and (2) counts affected apps in production run history.

Round 1 kept for reference

Round 1 ran seven models on five legacy-template briefs (coffee shop, batik store, salon booking, tech blog, event feedback), one run each, on 12 November 2026. Three models built a site. DeepSeek V4.1 Flash won the blind comparison on all five sites with 105 of 125, then Gemini 90 and DeepSeek V4 Pro 85. Four models never produced a site: GLM 5.2 and GLM 5.3 Flash sent the plan as a JSON string, and Seed 2.0 Pro and Seed 2.1 Turbo sent empty write arguments.

Correction, 12 November 2026. Round 1's pass and first-pass columns mostly measured a harness bug, not the models. Twelve of the thirteen failed first validation passes, and both builds that never passed, were the same error: the legacy templates ship a PocketBase client that switches to http://127.0.0.1:8090 when the page is served from 127.0.0.1, and the harness serves every build that way without exposing that port. Only one first-pass failure was a model's own. On reliability the three models that built sites were tied.

Round 2 is not a repeat of round 1. It uses app-base instead of the legacy templates, checks named collections and routes, runs three times per site, and ran GLM and Seed with the local patch. Read round 1 for the shape of the earlier failures, not for comparable numbers.

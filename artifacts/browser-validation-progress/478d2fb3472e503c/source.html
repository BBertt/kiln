Cold starts measured

Waking the preview is a separate wait

A sleeping preview has no running copy. In four staging rounds, its first page answered after a median of 20.89 seconds.

The six-page browser capture took 30.47 seconds after waking and 30.35 seconds while warm. These are medians, not guarantees.

The chat turn wakes the preview before the AI call. This wake-up wait comes before browser validation, not inside it.

Failure handling needs attention

Memory limits affect browser results

The local container had a 1 GiB memory limit. Five concurrent captures triggered process kills, and eight concurrent captures produced no complete captures.

At eight captures, five incomplete results returned a passing console-only verdict. This does not prove that a complete generation turn passes incorrectly.

Two captures completed with memory headroom in this browser-only setup. This is not a safe concurrency limit for the complete API.

What the timing change delivers

MR !697 records browser startup and shutdown time. For each route, it records page opening, navigation, waiting, result collection, and page closing.

The admin console displays these values under Recorded facts → Browser capture. The MR contains a screenshot of the actual local console.

The screenshot uses a seeded demo run with real timing from the six-page local capture. It is not a production or staging turn.

The existing error controls still worked. A delayed JavaScript error and a broken image failed validation during the local tests.

The API and admin console must deploy together so that the console can read the new timing records.

Where each checkpoint stands

BV-1 · No more tests needed

Explain the delay

The local tests cover per-step timings, concurrent captures, and error controls. Staging tests cover sleeping previews and captures after waking.

The existing production data and completed local and staging tests are enough for the diagnosis. No additional first-build or edit tests are required.

This decision ends further BV-1 testing. Complete AI turns with the new timing remain untested, and retries were not observed.

BV-2 · Agreement pending

Agree on the design and time limits

BV-2 sets acceptable times for normal and slow runs. It also defines timeouts, capacity limits, cancellation, cleanup, and failure results.

The design must explain where browsers run outside the API. It must also map future browser needs to supported now, addable later, or unmet.

Jonathan and Bertrand must accept that mapping or record exceptions. This checkpoint is a design agreement, not another staging test.

BV-3 · Not delivered

Build the agreed changes

BV-3 moves browser execution outside the API resource and lifecycle boundary. It also addresses the measured causes of delay.

A crash, timeout, or lack of capacity must produce an explicit result. A browser task that did not run must never count as a pass.

The four-second wait is a measured target for improvement. Its replacement still needs a design that preserves error detection.

BV-4 · Not delivered

Compare, release, and observe

BV-4 compares the new behavior against the measurements on this page. It covers complete first-build and edit turns, including concurrent work.

The comparison must show that errors remain detectable. It must also show that failed browser execution stays distinct from a clean result.

Staging evidence, a reviewed release, production evidence, and updated operating guidance complete this checkpoint.

What comes next

  1. Start BV-2 with the existing measurements. Agree on time limits, the browser design, and support for future browser needs.

  2. Review MR !697 and deploy the timing change after approval. Its deployment does not block the BV-2 design discussion.

  3. Implement BV-3, then compare results and complete the release evidence under BV-4.

No further diagnosis tests are required before BV-2. Tests after future code changes remain part of BV-3 and BV-4.

These are proposed next steps, not completed work. No speed target, new wait strategy, or production capacity limit is agreed yet.

Local tests establish the baseline and expose failure risks. They do not prove complete turn behavior or the safety of a deployed capacity limit.

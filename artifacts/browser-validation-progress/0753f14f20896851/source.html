BV-1 findings: why the console check is slow

The answer

The console check is slow because it visits pages one at a time and waits a fixed four seconds on each page. An app with more pages takes longer. The check does not slow down at random.

A route is a page address in the generated app. The console check is the browser check that looks for page errors on each route.

Three sources gave this result: production run history, local tests with the API image, and staging tests with a sleeping preview. No more tests are needed for BV-1.

Production data

1. Page count sets the check time

Production run history recorded 167 console checks from 13 October to 4 November. Their times fit 0.7 seconds plus 4.7 seconds for each route, with a correlation of 1.00.

The earlier reports of random delays came from apps of different sizes. The median check took 57 seconds. 68 of the 167 checks (41%) took more than one minute, and the largest apps took about two minutes.

Staging tests

3. A sleeping preview adds a wait before the check

A preview sleeps after 300 seconds without use. A sleeping preview has no running copy. Four staging rounds woke the six-page tiket.com preview and then ran the check.

The first page answered after a median of 20.89 seconds. The check right after waking took 30.47 seconds. The check on a warm preview took 30.35 seconds.

The chat turn wakes the preview before the AI call. So the wake-up wait comes before the check, not inside it. Only the first page load was about 0.65 seconds slower after waking.

Staging tests

4. One check did not harm the API

During one check on staging, API process memory peaked at 737 to 754 MiB of its 1 GiB limit. That figure includes the test script, which a real turn does not add.

The API health check never failed. Its median answer took 7 to 9 ms, and its slowest took 197 ms. The container did not restart and no process was killed.

The container reached its memory limit with file cache. The system freed that cache without a failure.

All tests

6. The check still catches real errors

A clean page passed. A JavaScript error delayed by 3.2 seconds failed the check. A broken image also failed the check.

The timing change measures the check. It does not change which errors the check finds.

Production data

7. A second delay sits outside the check

Before validation starts, the API sends the new files to the preview. Users wait through this step too.

In production, this step took a median of 4.7 seconds, 26.5 seconds at the 90th percentile, and 102.6 seconds at worst. It is not part of the console check. It belongs in the total time budget.

What BV-1 does not cover

Complete AI turns did not run with the new step timing, and no retries were seen. Bertrand decided that the existing evidence is enough to move to BV-2.

137 of the 167 production checks came from 2 of 14 apps. The data hides app identities, so it does not show whether those apps belong to customers or to internal tests.

The local concurrency limits are not a safe limit for the full API or for production. Local preview copies had no customer data. External assets and fonts loaded from the internet.

What this means for BV-2

Moving the browser out of the API protects the API, but it does not shorten the wait. A faster check needs fewer seconds of waiting or more pages checked at once.

A shorter wait can miss late errors that the check finds today. Checking pages at the same time costs memory. The BV-2 proposal below keeps the full wait and checks two pages at once.

Every incomplete check must return an explicit result, never a pass.

What the timing change delivers

MR !697 records browser startup and shutdown time. For each route, it records page opening, navigation, waiting, result collection, and page closing.

The admin console displays these values under Recorded facts → Browser capture. The MR contains a screenshot of the actual local console.

The screenshot uses a seeded demo run with real timing from the six-page local capture. It is not a production or staging turn.

The existing error controls still worked. A delayed JavaScript error and a broken image failed validation during the local tests.

The API and admin console must deploy together so that the console can read the new timing records.

BV-2 proposal: a separate browser runner

This is a proposal for review, not an approved design or a completed implementation. No more BV-1 tests are required.

MR !697 is merged into staging, as reported by Bertrand. BV-2 can now focus on the design and its limits.

The recommendation

A runner is a service that performs browser work. Run it as an always-running deployment in the existing Kubernetes cluster, separate from the API host.

Keep Playwright and Chromium. Start one fresh browser per request and visit up to two routes at once, each in a separate browser context.

A browser context keeps cookies and page state separate. Keep the current four-second observation window for every route.

[INFERENCE] This proposal can reduce elapsed time by overlapping page visits, not by observing each page for less time. Browser separation alone does not remove the waits.

Do not create a Kubernetes Job for each validation request. Keeping the runner ready avoids adding job startup time to every turn.

What stays in the API

The test step selects the current routes and waits for the staged preview to be ready. It sends the approved preview address and route list to the runner.

The API evaluates findings through the existing checks and records attempts through the existing observer. It retains ownership of repair, saved files, and the final turn result.

The runner cannot change app files, call an AI model, or decide whether the turn succeeds. Existing static checks remain where they run today.

What the runner returns

The request identifies the run, validation attempt, preview, routes, and execution deadline. It does not contain source files, database credentials, or customer login credentials.

The response identifies every requested route as completed or incomplete. It includes existing findings, stage timings, execution status, and reasons for incomplete work.

Keep partial findings even when navigation or execution fails. Missing routes, failed probes, and truncated responses must never become a clean pass.

Capacity and time limits to approve

These values are proposed starting limits, not measured capacity guarantees. Keep them in code beside the failure policy, as RFC-030 requires.

Start with one runner replica, one active request, two concurrent pages, two CPUs, and a 2 GiB memory limit. Do not scale automatically initially.

Reject a request immediately when the runner is busy. Do not hide excess demand in a queue or launch browsers inside the API as a fallback.

Keep the existing 15-second navigation limit and four-second observation window. Cap each route at 25 seconds, including its probes.

For N routes, cap execution at the smaller of 180 seconds and 10 + 25 × ceil(N / 2) seconds. Here, ceil rounds up.

Reserve five seconds for forced cleanup outside that execution limit. Give connection and admission at most two seconds.

The turn runner decides whether a new test attempt fits its allowance before starting it. This proposal does not change the existing whole-turn allowance.

The execution limit also bounds the network request and any response processing. Probes and diagnostic requests cannot extend it.

Speed targets to approve

A percentile describes how many runs finish within a time. The 95th percentile means that 95 out of 100 runs finish within that time.

For healthy previews with up to six routes, propose a median browser time of 18 seconds and a 95th-percentile time of 25 seconds.

For the complete existing validation pass, propose a median of 25 seconds and a 95th-percentile time of 35 seconds on that same workload.

These targets start after preview readiness and include runner communication and cleanup. They exclude AI calls, repairs, and preview wake-up.

Larger apps retain all current routes. Their initial target is at least 30% less browser time than their comparable serial baseline.

Do not count incomplete work as a fast success. Report incomplete requests, busy responses, and execution failures separately from successful timing results.

The six-route staging baseline is about 30 seconds. Two concurrent page visits make these targets plausible, but BV-3 and BV-4 must demonstrate them.

Failures and cancellation

Use explicit outcomes for completed work, incomplete work, busy capacity, unavailable runner, timeout, and cancellation. Implementation must use enums for these named choices.

App errors remain findings for the existing repair policy. Runner failures report that the change could not be fully tested, not that generated code needs repair.

The existing turn failure policy decides the final outcome. This proposal does not add automatic repair rounds or restore a staged change because the browser failed.

A cancellation request closes the active contexts and browser. If graceful cleanup exceeds five seconds, kill the browser process group.

The runner enforces its deadline even if the API disappears. A lost connection cancels the request when detected, and the deadline bounds any abandoned work.

Use the attempt ID to prevent duplicate execution. Keep that identity until the deadline and cleanup period expire, and do not retry automatically.

A runner restart ends active work as unavailable. The API must never infer success from an empty response or a lost request.

Access and resource separation

The service is private and accepts authenticated calls only from the API. It has no public ingress and no access to platform database credentials.

The API derives the preview address from its deployment record. The runner accepts only approved preview destinations, not arbitrary addresses supplied by a user.

Browser pages can load public assets, but cannot reach cloud metadata, loopback addresses, or unrelated private services. Approved preview access is the explicit exception.

Enforce those restrictions on redirects and browser subrequests as well as the first navigation. Network policy must prevent address changes from bypassing them.

Run browser processes without host mounts or privileged access. Give the deployment explicit CPU, memory, and process limits.

The cluster placement, private authentication, and network rules need infrastructure and security review before implementation. This artifact authorizes no deployment changes.

Why not reuse the general worker?

The repository already uses Taskiq and Redis for background work. This browser operation belongs to a live test attempt with a bounded response time.

A direct private request avoids adding durable queue state and delayed work against an outdated preview. The runner owns only its current bounded request.

The general worker remains unchanged. Moving the complete generation turn into a durable job remains outside this outcome.

The existing thumbnail path already uses Kubernetes Jobs. It remains separate and does not replace the always-running validation runner.

Compatibility with the later browser work

This is the proposed focused RFC-029 mapping. Supported now describes the current behavior, not an unbuilt service.

Addable later means the boundary permits the capability, but this outcome does not implement it. Jonathan and Bertrand must accept this mapping or record exceptions.

  • Supported now: Chromium visits the staged preview and gathers console, network, image, and rendered-page findings. Existing attempts record findings and timing.

  • Addable later: phone viewports, touch input, scripted interactions, screenshots, filmstrips, and DevTools traces. Their execution stays within the test step.

  • Addable later: evidence files in object storage, associated with a run and attempt, with retention defined alongside run history.

  • Addable later: new recording, suggesting, and blocking checks through generation interfaces. The runner reports observations, while the turn owns modes and repair decisions.

  • Outside this outcome: customer login sessions, new visual checks, vision-model calls, and a Chromium replacement. These are not promised by this proposal.

Post-turn reviews can only record results. They cannot reopen a completed turn or create a separate repair loop.

Implementation, release, and rollback

Record the approved boundary in an RFC or ADR, as ADR-042 requires. Then implement the service and API adapter under BV-3.

First move the current behavior unchanged. Then enable two-page concurrency as a separate change so that failures have a clear cause.

Use the existing local workload for before-and-after comparisons. Include delayed errors, broken images, unreachable pages, probe failures, cancellation, runner crashes, and exhausted capacity.

These are tests of new code, not more BV-1 diagnosis. BV-4 covers staging release evidence and observation after production rollout.

Deploy the runner before switching API calls to it. Migrate production and eval callers together, then remove the obsolete in-API capture path and browser dependencies.

If two-page concurrency causes problems, return the runner to one page at a time. This preserves browser separation while giving up the speed gain.

If the remote execution boundary fails, roll back the reviewed API and runner release together. Do not silently fall back to in-API browsers.

Release evidence must cover API health, complete route coverage, runner memory, duration, and explicit failure results. A faster result with lost findings does not meet the target.

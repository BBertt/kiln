Agent harness or gated workflow for Arcane generation?

A full agent harness is not worth building. A bounded write loop with real feedback is. Token spend pays best on verification, not on free tool choice.

Verdict: selective 13-build baseline 2 loop spikes Not yet run on BytePlus

The baseline is 13 first builds: 4 passed first try, 8 passed after a fix, 1 failed. The loop figures come from Gemini-era spikes. No BytePlus call was made for this page.

Options 4

Full agent harness

Rejected

The model chooses among read, search, edit and run tools, and decides when it is done.

Breaks the plan-card UX and the plan-as-permission boundary. Every surveyed harness leans on a human approver or a sandbox. Arcane has neither.

Bounded write loop

Recommended

One write event at the end, plan immutable, feedback from the write gate, static analysis and planned-file coverage.

Measured wins: first edit in 8 to 12 seconds instead of a 3m14s frozen card, and a bad anchor costs one iteration. Cheap tokens remove the 8x objection; a cap stays.

Read loop before plan

Deferred

Paths-only, complete file index, hard cap. The model asks for the files it needs.

Recall rose from 4/7 to 6/7 at about double the input tokens. The remaining miss was judgement, not capability, so it did not fix the visible bug.

Plan-completeness check

Recommended first

Grep the app for the old value and require the plan to cover every file that still contains it.

The two-tone app survived every loop. Code notices the files the model did not. This is a plan-gate rule, not an agent.

Recommendation 5 steps

  1. Check BytePlus's context window and cache behavior first. If the app fits, raise the file-dump budget and skip the read loop. One config change beats a new phase.
  2. Re-run the loop PoC on BytePlus: does it iterate and terminate, reproduce anchors, honor forced tool choice, stream arguments, and cache the prefix?
  3. Build one bounded loop in the write step. Pass the tools in, keep the plan immutable, end with one write event, and cap iterations at roughly 3 per planned file.
  4. Add the deterministic plan-completeness check. It is cheaper than the loop and addresses the user-visible bug the loop did not fix.
  5. Spend the rest of the quota offline: a wider eval corpus, more rounds, and multi-candidate builds judged offline. No user waits for those tokens.

What could not be tested 3

  • BytePlus behavior. Every loop number here is a Gemini measurement. A different model can iterate better or worse, cache differently, or fail anchors more often.
  • Finished-app quality from the read loop. Recall of ground-truth files was measured, not whether the site was better after the turn.
  • In-loop static analysis. It is not built, so there is no measurement of fewer fix rounds or fewer broken builds.

Method and limits

  • Baseline: 13 first builds on the production model chain, one provider, Docker render on. Loop figures come from one 6-file write-loop turn and a three-variant read-loop PoC, with n of 2 or less in places.
  • Cost comes from the token ledger. Cached tokens are priced at the cache-read rate. The 8x is one turn, not a distribution.
  • The write loop was measured before the gated-turn rewrite. The current pipeline already sends a failed write back through its gate, so the loop's marginal value is lower on edits and higher on first builds.
  • Several Gemini workarounds may not apply to BytePlus: one tool per phase, argument bursts, thought signatures, and an uncacheable conversation tail.

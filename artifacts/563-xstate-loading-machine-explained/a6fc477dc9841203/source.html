How XState runs the editor's loading flow

Issue #563 · MR !718 · explains apps/web/src/domains/editor/preview/preview-loading.machine.ts at commit 25ac80b0 · compared with the code it replaced on staging

The preview panel has to decide what to show from many signals that change at different times. Before this MR, that decision was spread over three hooks, a provider and a render function. Each had its own state, its own timers, and rules that depended on the others. Now one XState machine holds all of it. XState is a library for state machines: you write the states, the events and the rules for moving between states as plain data, and the library runs them.

This page explains what the machine does, how its parts map to XState ideas, and how the same rules looked without it. It also says what XState cost us.

What the machine has to decide

Every moment, the preview panel shows exactly one main screen, plus up to three layers on top of it:

  • The main screen: a skeleton, the workspace check (Verifying), the workspace start (Provisioning), the first-build scene, the live preview, or a status message such as "failed" or "timed out".
  • The build overlay, with one of the ten #556 animations, which fades in and out.
  • The wake-up overlay, while the preview page starts, and its error panel.
  • The testing badge, while the AI validates or repairs the site.

The inputs arrive from four places: the live chat stream, the build record the server saves, the deployment status the editor polls every few seconds, and messages from the preview page. On top of that, five timers matter: a 60-second limit for the workspace start, a 4-second bridge after a build ends, two 0.5-second fades, and a 30-second safety limit for the wake-up overlay.

Before: the state was spread out

Each box below kept its own piece of state with React hooks (useState, useReducer, useRef) and started its own timers in effects. The red dashed lines are rules that crossed file boundaries. For example, the wake-up overlay was hidden because a prop was set from the build overlay's phase, in a third file.

This code worked. Its difficulty was that no single place described the whole flow. To answer "what does the user see if the preview page reports ready while a build is fading out?", a reviewer had to read all five files and simulate the effects in their head.

After: one machine owns the decisions

The inputs did not change. One hook, usePreviewLoadingViewModel, reads them and sends a single OBSERVE event to the machine. The provider forwards checked iframe messages as events. The machine updates its state, and a selector, selectPreviewLoading, turns that state into what to render. The components no longer decide anything; they render what the selector returns.

The machine never touches the browser or the query cache. When it needs a side effect, it emits a named event (sendLifecycleInit, invalidateDeployment), and the provider performs it. That keeps the machine pure data that a test can run without React.

The five regions

Each region answers one question. Because they are parallel, a change in one region never resets another by accident, and each region's timers belong to that region only.

  • provisioning runs the 60-second limit for starting a workspace. When it expires, the screen shows the timeout message.
  • activity answers "is a build running?". When a build ends, it enters bridging and asks for a fresh deployment status. It holds the build overlay for up to 4 seconds, until the server reports syncing.
  • generation is the build overlay: hidden, visible or fading. It shows while a build runs, syncs or bridges, and steps aside during validating and repairing.
  • coldStart is the wake-up overlay. It follows the preview page's messages, with a 30-second safety limit and an error state.
  • screen picks the main screen. On every observation it re-decides, checking its rules in a fixed order.

The regions during a real build

This is the first build recorded for !718, redrawn from its debug log. Each row is a region; each bar is how long it stayed in a state. About five minutes of writing code are cut out of the middle.

Read the end from left to right. During validating and repairing, generation fades and hides, so the preview shows the testing badge. When the build ends, activity enters bridging and the overlay comes back for 4 seconds. Meanwhile screen switches to the preview, the iframe loads, and coldStart runs its own short visible-and-fade cycle. When the bridge timer ends, the overlay fades and the site is visible. Each region moved on its own clock, and nothing had to coordinate them by hand.

The phase row is not a region. It is the build phase in the machine's context, which the animation follows. The short validating* just after updating_preview is a stale value from the last poll, explained in "What XState does not fix" below.

The same rules, written both ways

1. The 4-second bridge after a build

Without XState
use-preview-generation-overlay.ts
const prevIsGenerating = useRef(isGenerating);
const [bridging, setBridging] = useState(false);

useEffect(() => {
  // detect the "build ended" edge by hand
  const wasGenerating = prevIsGenerating.current;
  prevIsGenerating.current = isGenerating;
  if (!wasGenerating || isGenerating) return;
  setBridging(true);
  void queryClientRef.current.invalidateQueries(/* app GET */);
  const id = setTimeout(() => setBridging(false), BRIDGE_MS);
  // remember to cancel it
  return () => clearTimeout(id);
}, [isGenerating]);

// a second effect ends the bridge early
useEffect(() => {
  if (isSyncing && bridging) setBridging(false);
}, [isSyncing, bridging]);
With XState
preview-loading.machine.ts
activity: {
  initial: "idle",
  states: {
    idle: {
      always: { guard: "isGenerating", target: "generating" },
    },
    generating: {
      always: {
        guard: "generationEnded",
        target: "bridging",
        actions: "invalidateDeployment",
      },
    },
    bridging: {
      always: [
        { guard: "isGenerating", target: "generating" },
        { guard: "isSyncing", target: "idle" },
      ],
      // the timer dies when the state is left
      after: { generationBridge: "idle" },
    },
  },
},

Without XState, the hook had to remember the previous value in a ref to spot the moment a build ended, start a timer, cancel it in a cleanup, and use a second effect to end the bridge early. With XState, bridging is a state. Entering it starts the timer. Leaving it for any reason (a new build, syncing seen, or the timer itself) cancels the timer. There is no previous-value ref and no cleanup to forget.

2. "A timeout must never clear an error"

Without XState
preview-provider.tsx
const beginFade = useCallback((fromError = false) => {
  clearTimeout(timeoutRef.current);
  setLifecycle((current) => {
    if (current.phase === "hidden") return current;
    // The safety timeout must NOT fade an error.
    if (current.phase === "error" && !fromError)
      return current;
    return { phase: "fading", error: null };
  });
  fadeRef.current = setTimeout(
    () => setLifecycle({ phase: "hidden", error: null }), FADE_MS);
}, []);
// …and every caller must pass the right fromError flag.
With XState
preview-loading.machine.ts
visible: {
  after: {
    lifecycleInit: { actions: "sendLifecycleInit" },
    // the 30 s safety timer lives here
    coldStartDeadline: "fading",
  },
  on: {
    FRAME_READY: { target: "fading", actions: "sendLifecycleInit" },
  },
},
error: {
  // No `after` in this state: no timer can ever fire here.
  on: {
    FRAME_READY: {
      target: "fading",
      actions: ["clearFrameError", "sendLifecycleInit"],
    },
  },
},

Before, the rule was an if inside a shared function plus a flag that every caller had to pass correctly. After, the rule is structural. The 30-second timer belongs to the visible state, and the error state has no timer at all. A timeout cannot clear an error because, while in error, no timer exists to fire.

3. Which screen wins

Without XState
preview-content.tsx
// PreviewContent: the order of these checks IS the rule.
if (ensureState.isVerifying) return <PreviewLoadingScene … />;
if (activeGeneration?.is_bootstrap &&
    (status === "running" || status === "syncing"))
  return <PreviewLoadingScene … />;
switch (previewState.status) {
  case "running": case "syncing":
    return (<>
      <PreviewIframe … />
      <PreviewGenerationOverlay {...generationOverlay} />
      {isTesting && <PreviewTestingBadge />}
      <PreviewColdStartOverlay
        suppressed={generationOverlay.phase !== "hidden"} />
    </>);
  …
}
With XState
preview-loading.machine.ts + selectors
screen: {
  initial: "deciding",
  on: { RECONCILE: { target: ".deciding" } },
  states: {
    deciding: {
      always: [                       // first match wins, in this order
        { guard: "isVerifying", target: "verifying" },
        { guard: "isBootstrap", target: "bootstrap" },
        { guard: "isLoading", target: "loading" },
        { guard: "isTimedOut", target: "timeout" },
        { guard: "isProvisioning", target: "provisioning" },
        { guard: "isPreviewAvailable", target: "preview" },
        …
      ],
    },
  },
},
// selector: the cold-start overlay waits for the build overlay
showColdStart:
  snapshot.value.generation === "hidden" &&
  snapshot.value.coldStart !== "hidden"

Before, the order of if statements in a render function was the precedence, and the wake-up overlay learned about the build overlay through a prop. After, the order is an explicit list of named guards in the screen region, the cross-overlay rule is one line in the selector, and both appear in the generated diagram.

4. Testing a timer

Without XState
old preview-generation-overlay.test.tsx
// old overlay test: real timers, the test waits it out
await act(() => new Promise((r) =>
  setTimeout(r, PREVIEW_GENERATION_TO_SYNCING_BRIDGE_MS + 50)));
With XState
preview-loading.machine.test.ts
// machine test: a simulated clock, no React, no waiting
observe({ isGenerating: true });
observe({ isGenerating: false });
clock.increment(PREVIEW_GENERATION_TO_SYNCING_BRIDGE_MS - 1);
expect(view().generation.phase).toBe("visible");
clock.increment(1);
expect(view().generation.phase).toBe("fading");

The old test rendered the hook and really waited more than 4 seconds. The machine test drives a simulated clock, so it checks the exact millisecond the bridge ends, runs in a few milliseconds, and needs no rendering.

What it costs

CodeBeforeAfter
Loading-flow code (lines)about 670, in five filesabout 910, in seven files (the machine file alone is 304)
Dependenciesnonexstate 5.33.2 and @xstate/react 6.1.0; bundle size not yet measured for this app (Sitrep measured about 14 KiB gzipped)
  • More lines, not fewer. The machine is longer than the code it replaced, because every rule now has a name. The gain is in finding and checking rules, not in typing less.
  • New ideas to learn. Regions, guards, eventless transitions and delayed transitions are new to most of the team. The table above is the minimum a reader needs.
  • XState has its own traps. We hit one while recording the build. LOAD_ARMED used reenter: true on a move from a region to its own child. In a parallel machine that restarts every region, so each iframe load cut short the bridge and the fade. The tests had not caught it; the debug log did. Commit 2d808714 fixed it and added a regression test. The comment above LOAD_ARMED in the file explains the rule.
  • Eventless transitions run after every event. That is cheap here, but it means the guards must be quick and must not read anything outside the context.

What XState does not fix

The machine can only be as correct as its inputs. At the end of a build, the live stream stops before the next poll arrives. For about half a second, the machine still sees the last polled build record, which says Validating, and starts to fade the overlay. The old code had the same behaviour. XState makes it visible in the diagram and the log, but fixing it needs better data, such as clearing the cached record when the stream ends. That is a decision for LB-2.

How to change the machine

  1. Edit preview-loading.machine.ts. Add a state, a guard or a delay by name. Keep React and fetching out of it.
  2. If the screen output changes, update preview-loading.selectors.ts.
  3. Add a test in __tests__/preview-loading.machine.test.ts, using the simulated clock for anything timed.
  4. Run pnpm --dir apps/web vitest run src/domains/editor/preview/__tests__/preview-loading.machine.test.ts -u to regenerate the diagram, and review its diff.
  5. Run pnpm --dir apps/web test:editor-loading for the browser journeys, and check the result in the editor with localStorage.setItem("DEWA_PREVIEW_DEBUG", "1").

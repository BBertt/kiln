Which requests does the browser make? 2 reads · 1 workspace check

The backend reports generation progress and deployment state. The frontend combines those reports with iframe readiness. XState decides what the editor displays.

Adding phase to active_generations preserves it across a browser reload. It does not make the database the only retrieval path. The browser still receives phase through the live stream and the app GET.

RequestWhen the frontend uses itWhat the backend returnsFrontend receiver
POST /api/v1/chat/streamSends chat commands with app_id. A generation runs through this connection.An ongoing response stream. Its decoded state includes status and progress: phase, label, plan and file changes.ChatRuntimeProvider → chat runtime → BuildProgressMirror → build-progress store
GET /api/v1/apps/{app_id}Reads the app on load and polls it while the editor runs.A JSON snapshot with active_generation and current_dev_deployment.React Query, the shared cache of API results. Preview and chat hooks read the same cached app.
POST /api/v1/apps/{app_id}/deployments/dev/ensureChecks the workspace on editor load when an existing dev deployment is present, or on retry.The deployment response. The hook refreshes the app query.useEnsureDevDeployment. Its pending flag becomes isVerifying.

These are the requests relevant to this loading flow, not every editor endpoint. The API reads the database. The browser never connects to the database directly.

Polling means fetching the same endpoint repeatedly. The preview requests a new app snapshot every 5 seconds when running, and every 3 seconds otherwise. Chat recovery also requests it every 3 seconds while an active-generation marker exists. These hooks share a cache, not separate app endpoints.

The turn writes its phase into live chat state and persists progress on its active-generation marker. These are separate updates. The stream and a polled app response can briefly disagree.

What the backend gives the frontend

These are illustrative payload fragments, not a network capture. The left side shows decoded stream state, not the stream protocol. The right side shows app JSON. Omitted fields and example values are marked.

The stream supplies the plan and file receipts. BuildProgressMirror turns those into filesWritten and filesPlanned. The saved marker contains only phase, progress_label and is_bootstrap. It does not recover the live file counts.

Which phase wins if both paths have data?

// preview-loading.machine.ts: generationPhase
return context.progress
  ? (context.progress.phase ?? null)
  : (context.activeGeneration?.phase ?? null);

If live progress exists, its phase wins. If it does not, the saved marker supplies the phase. Live progress with a missing phase returns null, even when the saved marker has a phase.

This rule chooses the phase, not every display field. The overlay copy separately prefers the marker's progress_label. Live phase and displayed copy can therefore reflect different update times.

updating_preview is stream-only. The backend reports it after terminal persistence removes the marker. It does not recreate an active-generation row for that final step.

What changes when I reload? live turn vs recovered turn

While this tab has the live stream

  1. The browser sends the chat POST.
  2. The response keeps delivering chat state.
  3. The mirror copies live progress into the store.
  4. The phase rule uses that live progress.

After the browser reloads

  1. The original live connection is gone.
  2. The browser fetches the app GET.
  3. The saved marker says that generation is still running and supplies its phase.
  4. The editor polls until the marker clears, then refreshes chat history.

The reload path does not reconnect to the original generation stream. The saved marker keeps the editor informed while the backend continues.

The backend removes the marker when it saves the terminal result. The recovery hook then fetches the final chat history. During a live turn, the stream's completion callback refreshes the app instead.

One phase vocabulary, two delivery paths. The new column removes the need to infer phase from label text after a reload. It does not unify the stream and app response into one channel.

A running deployment does not prove that its iframe is ready. That is why the frontend needs browser messages as well as the app GET.

What does XState do with these inputs? no network requests

XState does not fetch the API, read the database, or decode the chat stream. usePreviewLoadingViewModel gathers the frontend values and sends one OBSERVE event when they change.

The actor, a running copy of the machine, updates its context and applies its rules. The selector turns its snapshot into display props. PreviewContent uses those props to draw a screen, overlays and an animation.

The actor can also emit a request to refresh deployment data. The provider handles it through React Query. Fresh app data returns through the same input path.

The sections below explain the frontend machinery behind this last step. Start with Frontend wiring for the event sequence, or Regions for the display rules.

  • Every loading rule in one file, each with a name.
  • Timers start and stop with their states; none is cancelled by hand.
  • A diagram generated from the code, and a test that fails when it is stale.
  • Timer tests that run in milliseconds, without React.

What it costs

  • About 240 more lines, and two new packages.
  • New ideas for the team: regions, guards, eventless and delayed transitions.
  • Its own traps: one reenter: true restarted every region on each iframe load.

What the machine decides 4 sources · 5 timers

At every moment the preview panel shows one main screen, plus up to three layers on top:

  • The main screen: a skeleton, the workspace check (Verifying), the workspace start (Provisioning), the first-build scene, the live preview, or a status message such as "failed" or "timed out".
  • The build overlay, with one of the ten #556 animations, which fades in and out.
  • The wake-up overlay while the preview page starts, and its error panel.
  • The testing badge, while the AI validates or repairs the site.

The inputs come from four sources: the live chat stream, the build record the server saves, the deployment status the editor polls every few seconds, and messages from the preview page. Five timers also matter: a 60-second limit for starting the workspace, a 4-second bridge after a build ends, two 0.5-second fades, and a 30-second safety limit for the wake-up overlay.

Before: the state was spread out 5 files

Each box kept its own state with React hooks (useState, useReducer, useRef) and started its own timers in effects. The red dashed lines are rules that crossed files. For example, the wake-up overlay was hidden by a prop set from the build overlay's phase, in a third file.

This code worked. Its difficulty was that no single place described the whole flow. To answer "what does the user see if the preview page reports ready while a build is fading out?", a reviewer had to read all five files and simulate the effects in their head.

After: one machine owns the decisions 1 machine

The inputs did not change. One hook, usePreviewLoadingViewModel, reads them and sends a single OBSERVE event. The provider forwards checked iframe messages as events. The machine updates its state, and a selector, selectPreviewLoading, turns that state into what to render. The components no longer decide anything.

The machine never touches the browser or the query cache. When it needs a side effect, it emits a named event (sendLifecycleInit, invalidateDeployment), and the provider performs it. That keeps the machine plain data that a test can run without React.

The files, before and after editor domain: 9 added · 2 deleted · 24 changed

Most of the change sits in one folder, apps/web/src/domains/editor/preview/. Two hooks were deleted, and the new machine, its selectors and the view model that feeds it were added next to the components that use them. The ten animation files were already there from #556; before this change nothing used them. The tree shows the loading-related files; the counts above cover the whole editor domain.

How the wiring works events in · snapshots out

Does the frontend just call the XState file? No. preview-loading.machine.ts is a blueprint: states, rules and timers written as data. Nothing calls a function in it. The editor makes one running copy of it, called an actor. Components talk to the actor in only two ways: they send it events, and they read its snapshots.

1 · create

PreviewProvider calls useActorRef(previewLoadingMachine). That creates one actor and starts it after the provider mounts. The editor remounts the provider for each app, so each app gets a fresh actor.

2 · input

Code sends events with loadingActor.send(…). The view model sends OBSERVE; the provider sends LOAD_ARMED and FRAME_*. Events sent before the actor starts wait in its mailbox.

3 · output

Each event produces a new snapshot. useSelector re-renders a component when its selected value changes. Effects come out as emitted events, which the provider handles with loadingActor.on(…).

The five regions 5

Each region answers one question. Because they run in parallel, a change in one region never resets another, and each region's timers belong to it alone.

  • provisioning runs the 60-second limit for starting a workspace. When it expires, the screen shows the timeout message.
  • activity answers "is a build running?". When a build ends it enters bridging, asks for fresh status, and holds the overlay up to 4 seconds until syncing is seen.
  • generation is the build overlay: hidden, visible or fading. It steps aside during validating and repairing.
  • coldStart is the wake-up overlay. It follows the preview page's messages, with a 30-second safety limit and an error state.
  • screen picks the main screen. It re-decides on every observation, checking its rules in a fixed order.

Phases and regions 10 phases · 1 region reacts

A region is the editor's own state: the machine moves it, by its rules and timers. The phase is data from the backend, stored in the machine's context: the machine only reads it. Each region reads a few inputs, and only one region, generation, reads the phase at all.

PhaseRegion it changesWhat the reader sees
preparing, planning, writing_code, making_images, syncingnonePicks the animation in the build overlay, or in the first-build scene
saving_files, updating_previewnoneShows the Syncing animation
validating, repairinggeneration: the isTesting guard turns true, so the overlay fades and hidesTesting badge with a small Validating or Repairing animation; the preview stays visible. On a first build the full scene stays (decision 4)
none, or a value the editor does not knownoneToday's generic loading scene, with no phase animation

Three animations do not come from a phase at all. Verifying and Provisioning come from the screen region, and Cold start comes from the coldStart region.

Planning and writing are both just generating to the activity region. The machine does not copy the backend's steps into regions, because the backend already runs its own state machine for them, and its steps can go backwards. The editor only needs to know whether the AI is testing, and which animation to draw.

The same rules, written both ways 5 comparisons

1. The 4-second bridge after a build

Without XState, the hook kept the previous value in a ref to spot the end of a build, started a timer, cancelled it in a cleanup, and used a second effect to end the bridge early. With XState, bridging is a state: entering it starts the timer, and leaving it for any reason cancels the timer.

2. "A timeout must never clear an error"

Before, the rule was an if in a shared function plus a flag that every caller had to pass correctly. After, the rule is built into the structure: the 30-second timer belongs to visible, and error has no timer, so nothing can fire there.

3. Which screen wins

Before, the order of if statements in a render function was the precedence, and the wake-up overlay learned about the build overlay through a prop. After, the order is an explicit list of named guards, the cross-overlay rule is one line in the selector, and both show in the generated diagram.

4. Testing a timer

The old test rendered the hook and really waited more than 4 seconds. The machine test moves a simulated clock, checks the exact millisecond the bridge ends, and runs without rendering.

5. How a state reaches the screen

The panel is four layers. Each layer is drawn from one field of the selector's output, so a component never works out on its own whether it should show.

Before, PreviewContent called three hooks and combined them in an if-chain, and each overlay also fetched its own data: the build overlay read the progress store, and the wake-up overlay read the provider's lifecycle and a suppressed prop. After, PreviewContent receives one ready-made object and switches on loading.screen, and each overlay draws exactly the props it is given. Changing which layer wins means changing the machine or the selector, never a component.

Costs

  • More lines. About 670 lines in five files became about 910 in seven; the machine file alone is 304. The gain is in finding and checking rules, not in typing less.
  • Two packages. xstate 5.33.2 and @xstate/react 6.1.0. The bundle cost for this app is not measured yet (Sitrep measured about 14 KiB gzipped).
  • New ideas to learn. The table of XState ideas above is the minimum a reader needs.
  • Its own traps. LOAD_ARMED once used reenter: true to move from a region to its own child. In a parallel machine that restarts every region, so each iframe load cut the bridge and the fade short. The debug log caught it, not the tests. Commit 2d808714 fixed it and added a regression test.

What XState does not fix. The machine is only as correct as its inputs. When a build ends, the live stream stops before the next poll arrives, so for about half a second the machine still sees the last polled build record, Validating, and starts to fade the overlay. The old code did the same. Fixing it needs better data, such as clearing the cached record when the stream ends. That is a decision for LB-2.

How to change the machine 5 steps

  1. 1
    Edit the machine

    Add a state, guard or delay by name in preview-loading.machine.ts. Keep React and fetching out of it.

  2. 2
    Update the selector

    If what the panel shows changes, update preview-loading.selectors.ts.

  3. 3
    Add a test

    Add it to __tests__/preview-loading.machine.test.ts, with the simulated clock for anything timed.

  4. 4
    Regenerate the diagram

    Run pnpm --dir apps/web vitest run src/domains/editor/preview/__tests__/preview-loading.machine.test.ts -u and review the diagram's diff.

  5. 5
    Check it in a browser

    Run pnpm --dir apps/web test:editor-loading, then open the editor with localStorage.setItem("DEWA_PREVIEW_DEBUG", "1") and watch the log.

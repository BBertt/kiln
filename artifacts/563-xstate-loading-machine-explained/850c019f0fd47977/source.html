What changed

The editor used to read three server shapes. It now reads one object, EditorState, from two paths. While a build turn streams, every generation field comes from the stream. The preview fields always come from the GET.

The label is not stored. The server computes it from the phase. The GET also fills the preview fields from the development deployment row, and it never fills the file counts.

The frontend deletes derivePreviewState, preview-state.ts, build-progress-store.ts, build-progress-mirror.tsx and the client-side file counting. It adds select-editor-state.ts, live-editor-state-store.ts, live-editor-state-mirror.tsx and use-generating-editor-state.ts.

Which requests does the browser make? 2 reads · 1 stream · 1 check

The backend now reports the editor's own state as one object, EditorState. Two paths deliver it. The editor-state GET returns the saved state. The chat stream sends live state while a turn runs.

These are the requests relevant to this loading flow, not every editor endpoint. The backend reads the database. The browser never connects to the database directly.

Polling means fetching the same endpoint again on a timer. The interval follows the preview. While the preview runs, the editor polls the editor state every 5 seconds. In every other state it polls every 3 seconds. A build is the busy case, so it gets the faster poll.

Before this change, the editor read active_generation and current_dev_deployment from the app GET. It now reads one EditorState from a dedicated endpoint, so the view model parses nothing.

Two other events refresh the caches. When the preview status or URL changes, the editor refetches the app GET. That keeps the admin panel, the publish link and the suggestion chips current. When the ensure request finishes, both queries are marked stale.

The turn writes its phase into live chat state. It also saves the phase on its active-generation marker. The phase therefore arrives from two places. The stream pushes it during the turn. The editor-state GET returns it from the marker and the deployment row.

What each path carries

These are example payloads, not a network capture. The field names are real. The values marked as examples are invented for this page. Fields that are always null on that path are marked too.

The stream starts its file count at 0, and the count only rises. The GET never reports a count, because the saved marker keeps none. The stream fills editorState when a build turn runs. It is null when the turn ends, and absent on question turns.

Which fields win if both paths have data?

// apps/web/src/domains/editor/preview/select-editor-state.ts
export function selectEditorState(
  savedEditorState: EditorState | undefined,
  liveEditorState: EditorState | null,
  isLiveRequest: boolean
): EditorState | null {
  if (!savedEditorState) return null;

  if (liveEditorState) {
    return {
      ...savedEditorState,
      is_generating: true,
      is_bootstrap: liveEditorState.is_bootstrap,
      phase: liveEditorState.phase ?? null,
      label: liveEditorState.label ?? null,
      files_written: liveEditorState.files_written ?? null,
      files_planned: liveEditorState.files_planned ?? null,
    };
  }

  return {
    ...savedEditorState,
    is_generating: savedEditorState.is_generating || isLiveRequest,
  };
}

While the stream has an editorState, its generation fields win as a group. A live null phase stays null. The editor never falls back to the saved phase during a live turn. The preview fields always come from the saved side, because only the GET reads the deployment.

With no live state, the saved object is the whole answer. One extra flag still applies: a local chat request in flight also reads as generating.

updating_preview arrives only on the stream. It arrives with is_generating: true, after the backend deletes the saved marker. The editor-state GET can never report it.

What changes when I reload? live turn vs saved state

While this tab has the live stream

  1. The browser sends the chat POST.
  2. The response keeps delivering chat state, with editorState inside it.
  3. LiveEditorStateMirror copies that value into live-editor-state-store.
  4. The merge lets the live generation fields win, so the phase, label and file counts come from the stream.

After the browser reloads

  1. The original live connection is gone.
  2. The server prefetch and the client query fetch GET /api/v1/apps/{app_id}/editor-state.
  3. That one object supplies every field: phase, label, preview status and preview URL.
  4. The chat overlay polls the same GET every 3 s while is_generating is true. When it turns false, the editor refreshes chat history.

With no live stream, the GET is the only source. The saved marker holds the generation phase and is_bootstrap. The development deployment holds the preview status, the URL and the snapshot version. The backend joins them into one EditorState.

The saved marker keeps no file counts. After a reload, files_written and files_planned are null. The screen shows the phase and its label without an invented number. A mid-build reload in the live run brought back the saved screen and label, with no file count.

The label survives the reload because the backend derives it from the saved phase. Nothing has to read text back out of the database to find it.

One shape, two delivery paths. A reload loses the live file counts. It does not lose the phase, the label or the preview state, because the GET reads all three from the database.

When a live turn finishes, the chat runtime refreshes the app GET and the editor-state GET. A recovered turn waits for its own poll to report the end.

Which rows replaced which

  • progress and activeGeneration are now the generation fields of editorState. The stream still fills those fields live during a turn.

What does XState do with these inputs? no network requests

The view model gathers values. The actor applies display rules. The selector prepares props. The component draws them. Only the code outside the actor talks to the API.

The machine now observes three values: appId, editorState and isVerifying. Its regions, states, guards, timers and transitions did not change. The diagram generated from the machine is byte-identical.

The refresh loop is optional. When a turn ends, the actor emits invalidateDeployment. The provider marks the editor-state query and the app query stale. React Query fetches both again, and fresh values return through OBSERVE.

A second refresh runs outside the actor. The view model watches preview_status and preview_url. When either changes, it refetches the app GET, so the admin panel, the publish link and the suggestion chips stay current.

What XState gives

  • Every loading rule in one file, each with a name.
  • Timers start and stop with their states. No code cancels them by hand.
  • A diagram generated from the code, and a test that fails when it is stale.
  • Timer tests that run in milliseconds, without React.
  • One input shape, so the machine has nothing to guess.

What it costs

  • About 250 more lines, and two new packages.
  • New ideas for the team: regions, guards, eventless and delayed transitions.
  • Its own traps: one reenter: true restarted every region on each iframe load.
  • One merge rule to learn: while a turn streams, its fields win whole.
  • It cannot fix stale inputs.

What the machine decides 4 sources · 5 timers

At every moment the preview panel shows one main screen, plus up to three layers on top:

  • The main screen: a skeleton, the workspace check (Verifying), the workspace start (Provisioning), the first-build scene, the live preview, or a status message. The status message reads "failed" or "timed out".
  • The build overlay, with one of the ten #556 animations, which fades in and out.
  • The wake-up overlay while the preview page starts, and its error panel.
  • The testing badge, while the AI validates or repairs the site.

The inputs come from four places: the live chat stream, the editor-state GET, the workspace check, and messages from the preview page. The GET carries both the saved generation and the deployment, so those two now arrive in one response and in one shape. Five timers also matter. There is a 60-second limit for starting the workspace and a 4-second bridge after a build ends. Two 0.5-second fades follow, plus a 30-second safety limit for the wake-up overlay.

Before: the state was spread out 5 files

Each box kept its own state with React hooks (useState, useReducer, useRef) and started its own timers in effects. The red dashed lines are rules that crossed files. For example, the wake-up overlay was hidden by a prop set from the build overlay's phase, in a third file.

This code worked. Its difficulty was that no single place described the whole flow. To answer "what does the user see if the preview page reports ready while a build is fading out?", a reviewer had to read all five files and simulate the effects in their head.

After: one machine owns the decisions 1 shape · 1 machine

The inputs are one object now. usePreviewViewModel merges the live stream into the saved editor state with selectEditorState. usePreviewLoadingViewModel reads that object and the verify flag, then sends a single OBSERVE event. The provider forwards checked iframe messages as events. The machine updates its state, and a selector, selectPreviewLoading, turns that state into what to render. The components no longer decide anything.

Every region, state, guard, timer and transition stayed the same when the inputs merged. The machine never touches the browser or the query cache. When it needs a side effect, it emits a named event (sendLifecycleInit, invalidateDeployment), and the provider performs it. That keeps the machine plain data that a test can run without React.

How the wiring works events in · snapshots out

Does the frontend just call the XState file? No. preview-loading.machine.ts is a blueprint: states, rules and timers written as data. Nothing calls a function in it. The editor makes one running copy of it, called an actor. Components talk to the actor in only two ways: they send it events, and they read its snapshots.

1 · create

PreviewProvider calls useActorRef(previewLoadingMachine). That creates one actor and starts it after the provider mounts. The editor remounts the provider for each app, so each app gets a fresh actor.

2 · input

Code sends events with loadingActor.send(…). The view model sends OBSERVE with the current editor state. The provider sends LOAD_ARMED and FRAME_*. Events sent before the actor starts wait in its mailbox.

3 · output

Each event produces a new snapshot. useSelector re-renders a component when its selected value changes. Effects come out as emitted events, which the provider handles with loadingActor.on(…).

Black arrows are events going into the actor, green arrows are its output, and grey arrows are ordinary calls. The actor handles each event straight away, then waits. The only things it does on its own are its timers.

The five regions 5

Each region answers one question. Because they run in parallel, a change in one region never resets another, and each region's timers belong to it alone.

  • provisioning runs the 60-second limit for starting a workspace. When it expires, the screen shows the timeout message.
  • activity answers "is a build running?". When a build ends it enters bridging, asks for fresh status, and holds the overlay up to 4 seconds until syncing is seen.
  • generation is the build overlay: hidden, visible or fading. It steps aside during validating and repairing.
  • coldStart is the wake-up overlay. It follows the preview page's messages, with a 30-second safety limit and an error state.
  • screen picks the main screen. It re-decides on every observation, checking its rules in a fixed order.

Phases and regions 9 phases · 1 region reacts

A region is the editor's own state: the machine moves it, by its rules and timers. The phase is data from the backend, and it is one field of the editor state in the machine's context: the machine only reads it. Each region reads a few fields, and only one region, generation, reads the phase at all.

The label is not a separate input. The backend derives it from the phase with ProgressPhase.label. Migration b7e3c5a91d24 dropped the stored active_generations.progress_label, so no column can disagree with the phase. The editor state carries the label, filled from the phase.

The same rules, written both ways 5 comparisons

1. The 4-second bridge after a build

Without XState, the hook kept the previous value in a ref to spot the end of a build. It started a timer, cancelled it in a cleanup, and used a second effect to end the bridge early. With XState, bridging is a state: entering it starts the timer, and leaving it for any reason cancels the timer.

2. "A timeout must never clear an error"

Before, the rule was an if in a shared function plus a flag that every caller had to pass correctly. After, the rule is built into the structure: the 30-second timer belongs to visible, and error has no timer, so nothing can fire there.

3. Which screen wins

Before, the order of if statements in a render function was the precedence, and the wake-up overlay learned about the build overlay through a prop. After, the order is an explicit list of named guards. The cross-overlay rule is one line in the selector, and both show in the generated diagram.

4. Testing a timer

The old test rendered the hook and really waited more than 4 seconds. The machine test moves a simulated clock, checks the exact millisecond the bridge ends, and runs without rendering.

5. How a state reaches the screen

The panel is four layers. Each layer is drawn from one field of the selector's output, so a component never works out on its own what to draw.

Before, PreviewContent called three hooks and combined them in an if-chain. Each overlay also fetched its own data. The build overlay read the progress store, and the wake-up overlay read the provider's lifecycle and a suppressed prop. After, PreviewContent receives one ready-made object and switches on loading.screen, and each overlay draws exactly the props it is given. Changing which layer wins means changing the machine or the selector, never a component.

Costs

  • More code. About 670 lines in five files became about 916 in seven. The machine file alone is 293 lines. The gain is in finding and checking rules, not in typing less.
  • Two packages. xstate 5.33.2 and @xstate/react 6.1.0. The bundle cost for this app is not measured yet (Sitrep measured about 14 KiB gzipped).
  • New ideas to learn. The table of XState ideas above is the minimum a reader needs.
  • One merge rule. While a turn streams, the live generation fields win whole. A live null phase is a real "no phase", and the saved phase does not fill it in.
  • Its own traps. LOAD_ARMED once used reenter: true to move from a region to its own child. In a parallel machine that restarts every region, so each iframe load cut the bridge and the fade short. The debug log caught it, not the tests. Commit 2d808714 fixed it and added a regression test.

What XState does not fix. The machine is only as correct as its inputs. When a build ends, the stream stops sending its editor state. Until the next editor-state poll arrives, the machine still sees the last saved observation. That observation can still say a build runs at validating, so the overlay can fade late and the badge can flash. The old code had the same wait. Fixing it needs fresher data, such as an immediate refresh when the stream ends. That is a decision for LB-2.

How to change the machine 5 steps

  1. 1
    Edit the machine

    Add a state, guard or delay by name in preview-loading.machine.ts. Keep React and fetching out of it.

  2. 2
    Update the selector

    If what the panel shows changes, update preview-loading.selectors.ts.

  3. 3
    Add a test

    Add it to __tests__/preview-loading.machine.test.ts, with the simulated clock for anything timed.

  4. 4
    Regenerate the diagram

    Run pnpm --dir apps/web vitest run src/domains/editor/preview/__tests__/preview-loading.machine.test.ts -u and review the diagram's diff.

  5. 5
    Check it in a browser

    Run pnpm --dir apps/web test:editor-loading, then open the editor with localStorage.setItem("DEWA_PREVIEW_DEBUG", "1") and watch the log.

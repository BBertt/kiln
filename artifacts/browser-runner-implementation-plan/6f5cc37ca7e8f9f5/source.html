What changes

The browser leaves the API process. The API keeps the turn runner and calls a runner Deployment in the preview cluster.

In production a check takes about 0.7 s plus 4.7 s per route. The median check is 57 s, and the maximum is 118 s. The 4 s wait is 92% of the time.

The API keeps

The turn runner and the check code. A small client in browser_runner.py calls the runner with kept connections and makes three tries within 5 s after BUSY.

The runner owns

The browser process, one request slot, readiness and clean-up. Its image installs the API package with the validation extra, so it runs the same capture function.

Stays the same

The capture function and its models in browser_capture.py. The test step still turns COULD_NOT_RUN into KeptWarningReason.NOT_CHECKED, so neither the test step nor the turn runner changes.

One check, step by step

The API client sends one request. The runner takes it, loads two pages at once, returns the result and cleans up.

  1. The client keeps a connection to the Kubernetes API service proxy.
  2. The client sends the request with the attempt id, the preview URL, the routes and the deadline. The request travels on services/browser-runner:http/proxy.
  3. The replica takes its one slot and turns readiness false.
  4. The replica opens two pages at once through Traefik and KEDA. KEDA wakes a sleeping preview in about 21 s, before the check starts.
  5. Each page loads through the public preview address. After load, page 1 waits 4 s and page 2 waits 4 s.
  6. The check reads the console of each route and marks each route ok or not ok.
  7. The replica returns the result with the outcome and the unseen routes.
  8. The replica kills every other process and empties /tmp and /dev/shm.
  9. The replica turns ready again, and the Service can send the next request.

The BUSY branch: the proxy answers with no endpoints, or the replica answers BUSY. The client makes three tries within 5 s, then reports BUSY.

The check has a 180 s deadline. The service proxy carries a request for 200 s. The front proxy ends requests at 300 s.

What each answer means

6 outcomes

The runner answers with one outcome, and the API client sets some outcomes too. The check maps each outcome to a result.

The core rule: a route the browser did not see never passes. A seen page with an error still fails the check. Without a seen error, NoConsoleErrorsCheck gives COULD_NOT_RUN, and the change is kept with a warning.

A page that hung on its load event but reported a real error before that still fails the check, as today. A page that hung with no error is unseen, so the change is kept with a warning and does not go to a fix round.

Inside one runner replica

7 rules

A replica is one runner pod in the cluster. It takes one request at a time and answers ready only while it can take work.

One request at a time

The slot is one asyncio.Lock that is never waited on. A request that finds it taken gets BUSY at once.

Two pages at once

The capture function takes a number of pages at once. Staging runs one page at a time in phase 5, then two pages at once in phase 6. Each page keeps its 4 s wait after load.

2 CPU and 2 GiB

The Deployment asks for 2 CPU and 2 GiB as both request and limit.

180 s deadline

A stop signal gets a grace time of 190 s. That is the 180 s deadline, 5 s of clean-up and a margin.

No sandbox, clean-up after each check

Chromium runs without its sandbox. The pod's limits stand in for it. The root file system is read-only. After each check, the runner kills every process in its container except itself, empties /tmp and /dev/shm, then turns ready.

No restart after a count of checks

A replica does not restart after a count of checks, because Kubernetes delays a container that exits often.

Repeated requests get BUSY

The replica keeps the attempt ids of its current and recent requests until their deadline and clean-up time pass. A repeated id gets BUSY.

What goes into the cluster

3 namespaces

A namespace is a Kubernetes grouping for one environment. The preview cluster holds one runner namespace per environment, and each namespace holds the same objects.

Service proxy traffic comes in from the control-plane node's Weave address, 10.239.192.2 (spike F8). Outbound traffic reaches DNS, public addresses and the Traefik namespace on ports 80 and 443 (spike F7). Private ranges, the metadata address and the Kubernetes API are blocked.

The local API calls the dev runner through the same service proxy. It uses the dev cluster credentials and the dev runner token. The dev stack does not need a local runner container. Developers share the dev Deployment, not the staging or production Deployment.

The role follows the pattern that the builds namespace uses today. Each runner namespace binds its role to the platform service account of the same environment. Dev credentials must not grant access to staging or production runners.

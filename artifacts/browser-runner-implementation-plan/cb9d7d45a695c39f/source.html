Implementation plan: the browser runner

This plan describes delivery. RFC-032 describes the design.

This is a proposal, not an approved schedule. The plan stays as an artifact while the design is under review.

Status: draft plan. RFC-032 is not accepted yet, and this plan changes with the review · Date: 2026-11-10 · Author: Bertrand · Design: RFC-032 · Tracker: #610 (BV-3 and BV-4)

This page shows how RFC-032 gets built: the phases and their order, the files that change, the contract between the API and the runner, how one runner replica behaves, what goes into the cluster, how the rollout and the rollback work, and the tests for each phase. RFC-032 explains why. This page explains how. If the build proves part of this page wrong, the page is corrected first, with a dated note.

0 Summary

The work has eight phases. Phase 1 fixes today's code in the API, so that a page the browser never saw cannot pass. It needs no new infrastructure and can ship before the 25 Nov freeze. Phases 2 to 6 build the runner, put it in the cluster, and switch the API to it on staging, first with one page at a time and then with two. Phases 7 and 8 move production, measure BV-4, and remove Chromium from the API.

The forecast has the runner on staging before the freeze. Production timing remains a delivery decision in §12. The phases add up to about 18 working days, which is far more than the five days that #610 allows for delivery. The allowance needs a revision with Jonathan before phase 2 starts.

The runner image installs the API's package with the validation extra, the same way that the API image does today. The runner therefore runs the same capture function as the API and the local eval tools. The eval tools keep calling the function directly on a developer's machine.

The capture function is built so that phase 1 and the runner share it. In phase 1 the API calls it in its own process. From phase 5 the runner calls it, and the API only calls the client.

ConsoleCapture, RouteRenderCapture and CheckStatus exist today. Who sets each outcome, and what the check does with it:

Outcome Set by Check status What the user sees
COMPLETED The runner, or the API in phase 1 PASSED or FAILED, by today's rules As today
INCOMPLETE The runner, or the API in phase 1 FAILED if a seen page has an error. Otherwise COULD_NOT_RUN A fix round, or the change kept with the "not checked" warning
TIMED_OUT The runner, or the API in phase 1 As INCOMPLETE As INCOMPLETE
BUSY The runner, or the API client after three tries COULD_NOT_RUN with RUNNER_BUSY The change kept with the "not checked" warning
UNAVAILABLE The API client, when the connection breaks or fails COULD_NOT_RUN with RUNNER_UNAVAILABLE The change kept with the "not checked" warning
CANCELLED The API client, when the turn ends Not recorded as a check result Nothing. The turn already ended

The test step already turns a blocking check with COULD_NOT_RUN into KeptWarningReason.NOT_CHECKED. No change to the test step or to the turn runner is needed.

A page that hung on its load event but reported a real error before that still fails the check, as today. A page that hung with no error is unseen, so the change is kept with a warning and does not go to a fix round.

6 One runner replica

A replica moves through these states. Readiness is true only in Ready, so the Kubernetes Service sends new requests only to replicas in that state.

stateDiagram-v2
  [*] --> Starting
  Starting --> Ready: process up, liveness and readiness pass
  Ready --> Busy: takes a request, readiness turns false
  Busy --> Busy: another request gets BUSY at once
  Busy --> Closing: all routes done, deadline passed, or connection closed
  Closing --> Cleaning: browser closed within 5 s
  Closing --> Killing: browser still open after 5 s
  Killing --> Cleaning: process group killed
  Cleaning --> Ready: other processes killed, folders emptied, readiness turns true
  Ready --> Draining: deploy sends a stop signal
  Busy --> Draining: deploy sends a stop signal
  Draining --> [*]: no request left, or the grace time ends

Rules inside one replica:

  • The slot is one asyncio.Lock that is never waited on. A request that finds it taken gets BUSY at once.
  • The readiness answer reads the slot. It answers 503 while the slot is taken or the replica is draining.
  • The liveness answer only says that the process answers. A busy replica stays alive.
  • The replica keeps the attempt ids of its current and recent requests until their deadline and clean-up time pass. A repeated id gets BUSY.
  • Chromium starts in its own process group, so the replica can kill the browser and all its child processes at once.
  • The grace time on a stop signal is 190 s: the 180 s deadline, 5 s of clean-up and a margin.
  • Chromium starts with its sandbox off. After each check, the runner kills every process in its container except itself, then empties /tmp and /dev/shm. Only then does it turn ready again. The root file system is read-only, so nothing else survives a check.

The namespace names follow dewabuilder-browser-runner-<env>. A namespace groups the Kubernetes resources for one environment.

Environment Runner namespace API callers
Dev dewabuilder-browser-runner-dev Local API containers in developers' dev stacks
Staging dewabuilder-browser-runner-stg Staging API containers
Production dewabuilder-browser-runner-prod Production API containers

Each namespace contains a Deployment and a Service named browser-runner, plus its own token, access rules and network policies. Each Deployment starts with one replica. Developers share the dev Deployment, not the staging or production Deployment.

The local API calls the dev runner through the Kubernetes API service proxy. It uses the dev cluster credentials and the dev runner token. The runner opens each app through its public dev-preview address, through Traefik and KEDA. The dev stack does not need a local runner container.

The environments share cluster nodes and network capacity. Separate runners and resource limits reduce interference, but do not guarantee that dev or staging load cannot slow production.

The role follows the pattern that the builds namespace uses today. Each runner namespace binds its role to the platform service account of the same environment. Dev credentials must not grant access to staging or production runners. The local dev stack receives the dev runner token through its existing secret configuration, not through a committed value.

The objects to write:

Object Settings that matter
Namespace dewabuilder-browser-runner-dev, dewabuilder-browser-runner-stg and dewabuilder-browser-runner-prod
Deployment 1 replica to start. 2 CPU and 2 GiB as both request and limit. Rolling update with one extra pod and no pod down. Spread over nodes. No service account token. Not root. Read-only root file system with a temporary folder. Grace time 190 s

The comparison before each move uses the same three apps as BV-1 (Resep Dapur Ibu, Drinks at BVW and tiket.com) and real staging turns:

Move Must hold before it
One page at a time on staging The three apps give the same verdicts as the browser in the API. The times are within 2 s of today's, for the network cost. The clean page passes, and the delayed error and the broken image fail
Two pages at once on staging The same verdicts. The speed targets in RFC-032 §3.6 hold. The memory of a replica stays under its limit
Production A week of staging turns with no UNAVAILABLE that the team did not cause. The alert and the flag switch-back were both tried once
Removal BV-4 done in production. No flag switch-back for a week

Until phase 8, the flag is the rollback. It switches every new check back to the browser in the API, and it needs no deploy. After phase 8, the rollback is a release revert of the API and the runner together. The API never switches by itself.

12 Decisions to make during the build

  1. Decided: use dewabuilder-browser-runner-<env>, with dev, stg and prod. Developers share the dev runner in the cluster.
  2. The share of busy answers that adds a replica and fires the alert.
  3. The HTTP framework of the runner. This plan assumes FastAPI, which the API already uses, so the image adds no new library.
  4. Decided on 11 Nov 2026: Chromium runs without its sandbox, and the pod's limits stand in for it. The sandbox did not start in a locked-down pod on the cluster. After each check, the runner kills every other process in its container and empties its writable folders. A replica does not restart after a count of checks, because Kubernetes delays a container that exits often.
  5. Decided by the spike: no start-then-ask fallback. The service proxy carries a request for 200 s, and the front proxy ends requests at 300 s, above the 180 s deadline (spike F1).
  6. Decide whether the runner reaches production before or after the launch. The dates in §3 remain a forecast.

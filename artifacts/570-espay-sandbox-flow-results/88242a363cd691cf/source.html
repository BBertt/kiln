Espay sandbox: whole-flow test results

Issue #570 · tests run 9 November 2026, blocked tests re-run 10 November after Espay enabled the card endpoints · Espay sandbox only, dummy cards, no real money

One-time payments with Espay work end to end. Recurring card payments do not work on our sandbox merchant: Espay rejects every saved-card charge.

Pay once works

A card payment and a BCA virtual-account (bank transfer) payment were each created, paid, and confirmed by both Espay's payment callback and its status lookup. Espay added no fee to the IDR 10,000 price.

Auto-renew blocked

Espay enabled the card endpoints on 10 November. Charging a saved card now gets further but fails with IRF "Invalid Request". Refund, void and capture fail with a missing-privilege error. Nothing was charged or refunded.

Saving the card customer's choice

Espay's card page saves the card only if the customer ticks a box. Without it, Espay returns no token, so that customer could never be renewed.

What we learned

Saved-card charges still fail, now for different reasons

On 9 November every call under /rest/creditcard/… failed before Espay read it. After Espay enabled these endpoints on 10 November, two separate problems remain:

  • Renewal (tokenpayment): our signature is accepted (a deliberately wrong one now returns 11 "Credential is not Valid"), and Espay sends a signed inquiry for the renewal order. After we answer it, the charge returns IRF "Invalid Request". Changing the masked card's case or returning the token in our inquiry reply did not help. The most likely cause is the sandbox's identical placeholder token. Only Espay can confirm it.
  • Capture, void and refund: our merchant lacks a privilege named PGv2-PaymentRefundNotif. Espay has to grant it.

One new rule for our design: Espay asks us about a renewal order before charging it. If our system has not created that order first, Espay rejects the charge with 0031 "Error komunikasi dengan Mitra".

Saving the card is optional, and the token appears in only one place

  • Espay's card page shows a "Save card" box that starts unticked. A payment without it returns no token.
  • When ticked, the token arrives only in the payment callback. The status lookups never return it. If we miss that one callback, we lose the token.
  • For Auto-renew, we would have to make saving the card a condition of the subscription. Espay's page does not let us force the box.

Callbacks reach us, but are not signed

  • Every inquiry and payment callback from the sandbox arrived without a signature (X-SIGNATURE), although Espay's docs say they are signed. We cannot prove a callback came from Espay.
  • For these tests, our receiver accepts unsigned callbacks but still rejects a wrong signature. In production, the status lookup would have to be the source of truth.
  • Espay asks us for the bill (inquiry) at each step of the card page. One card order produced four inquiries.

A missed callback is not retried; it must be requested again

  • When our receiver failed, Espay marked the order Suspect and did not retry within 15 minutes.
  • Asking Espay to resend it works and fixes the status. Each resend carries a new delivery ID (paymentRequestId), so we would detect duplicates by order ID instead.

Fees

Our sandbox merchant is set to "Seller" fees. Espay reported txFee 0.00, and the customer paid exactly the price. Production fees are not known.

Smaller observations

  • Two routes reach the same Espay card page. Tests 1, 4 and the first run of test 2 used an undocumented shortcut: the page Embed Kit redirects to (sandbox-kit.espay.id/index/order), opened directly with our API key in the URL. Test 5b and the repeat of test 2 used the documented Host to Host API (POST /apimerchant/v1.0/debit/payment-host-to-host), which now works. Our demo now uses Host to Host only.
  • Once, in our headless test browser, Espay's Host to Host redirect page did not submit itself. The next Host to Host run submitted normally, so this was not consistent.
  • A virtual account created through Espay's older API still reports payment through the newer (SNAP) callback.

What these tests could not show

  • A way to list a customer's saved cards. None is documented in the pages we reviewed; we only have the token from the callback.
  • Whether a renewal needs the customer for an OTP, how declines look, and whether a renewal sends a callback. These need a working saved-card charge.
  • Duplicate charges and timeouts.
  • How long a token lasts, how to delete one, and what happens when a card expires.
  • Disputes, settlement reports and customer emails.
  • Whether production callbacks are signed.
  • QRIS payment, because the QRIS order was not paid.

Conclusion: how our Espay flow would work

This is our proposed design, built on what the sandbox showed. Steps marked blocked still need Espay to switch something on.

1. The first payment

Every paid subscription starts the same way, whether or not the customer saves their card.

  • Inquiry callback (step 4). Before taking payment, Espay asks us what the order costs. We answer from our own order record. If we don't know the order, or it has expired, we refuse and Espay stops. Espay can ask several times for one order; we saw four inquiries for a single card order.
  • Payment callback (step 6). Espay tells us the result. Status S means paid. If the customer ticked "Save card", this callback carries the card token. It is the only place we ever receive the token, so we must store it the moment the callback arrives.
  • Status lookup (step 7). The sandbox sends callbacks without a signature, so we can't prove a callback came from Espay. We treat the callback as a signal and the status lookup as proof. We grant the subscription only after the lookup confirms S and the right amount.
  • The return to our page (step 8) only tells us the customer came back. It never grants anything.

2. Card saved, or not saved

The customer decides on Espay's card page. The "Save card" box starts unticked, and we can't tick it for them. We only learn their choice from the payment callback: a token means they agreed; no token means they didn't.

Before checkout, our page has to say clearly that auto-renew needs the "Save card" box ticked. Espay's page doesn't explain this, and we can't change it.

3. When a payment callback doesn't arrive

Espay sends each payment callback once. In two tests, our receiver failed on purpose and Espay did not try again within 15 minutes. The order stayed SP (Suspect), even though the customer had paid. So we must chase missing callbacks ourselves.

  • A background job checks orders that are still unsettled after a few minutes. It asks Espay to resend the payment callback. In our tests the resend arrived within a second and moved the order from SP to S.
  • Each resend has a new delivery ID (paymentRequestId). So we grant access once per order ID, never once per callback.
  • An SP order has already been paid. We never charge the customer again because of it.
  • The resend request must use "Y". The docs say "N" marks the order as paid in Espay without telling us.

4. Renewal is blocked today

blocked Espay enabled /rest/creditcard/ on 10 November. Charging a saved card (tokenpayment) now passes the signature and inquiry checks, then returns IRF "Invalid Request" and the order stays IP. Capture, void and refund return "Privilege not found … PGv2-PaymentRefundNotif". Both need Espay: a chargeable sandbox token, and the missing privilege.

A renewal must create its order in our system before calling tokenpayment, because Espay sends an inquiry for it first, just as for the first payment.

Until then, only the Pay once path works end to end. The auto-renew path above is a design, not a tested flow. Once Espay enables it, we still need to test whether a renewal asks the customer for an OTP, whether it sends a payment callback, how declines look, and what happens if the same renewal is sent twice.
